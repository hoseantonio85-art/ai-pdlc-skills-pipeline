# Output contract — два документа, один сервис

## Пара артефактов

- `<slug>_service_context.md` — основное описание, **точно 13 разделов `## 0.`…`## 12.`**, по `PO_SERVICE_TEMPLATE.md`.
- `<slug>_questions_and_decisions.md` — постоянный реестр по `QUESTIONS_TEMPLATE.md`.

`slug` — английский/транслитерированный стабильный id сервиса, например `measures`, `incidents`, `agent_risks`; не меняй его от релиза к релизу. При обновлении не переименовывай готовые файлы без просьбы пользователя.

## Обязательные принципы

1. Полная анкета не равна «всё выяснено»: недостаток данных — `Требует уточнения`, а не выдуманный бизнес-процесс. Неприменимость — `Не применимо` только если механизма **нет**.
2. Сначала понятные **бизнес-формулировки**; технические поля, флаги, API и статусы — как ссылки/точные идентификаторы, где нужны.
3. Сценарии описывают контекст, участников, триггер, условия, ход, решение, альтернативу, исключение и следующий шаг.
4. Два документа согласованы: не должно быть «обязателен риск» в одном и «риск ИЛИ событие» в другом без маркированного конфликта.
5. Явно различай **фактическую дату бизнес-события**, **timestamp статуса/workflow** и **системную дату сохранения**, если они существуют.
6. Не объявляй вложения обязательными по наличию поля «отчёт»: тип источника и валидация требуют проверки.
7. Разделяй **бизнес-этап**, **техническое состояние**, **контрольный признак** («скоро/просрочено») и **уведомление** — пороги могут различаться.
8. Если пользователь выбрал код как AS IS, сохраняй источник (repo, путь, snapshot/commit), но не утверждай, что код находится в production.
9. Принятые решения `R-XX`, вопросы `Q-XX`, статусы фактов и ссылки на источники сохраняй при каждом уточнении.
10. Не копируй сырые БТ, код или документы целиком: сохраняй смысл, нужные точные условия и ссылки.

## В промежуточной сессии

Поддерживай краткий инкремент: что подтвердили, какая секция изменилась, что неизвестно, **один** следующий содержательный вопрос. Если есть доступ к файлам — сохраняй оба документа, но не дублируй их каждый ответ в чате.

## Финальное сообщение

Укажи (а) два готовых файла/пути, (б) статус `рабочий`, `PO-reviewed` или `approved` **только если есть явное подтверждение**, (в) число/темы оставшихся P0/P1 вопросов, (г) что проверялось — интервью/документы/код/production, (д) handoff для контекст-менеджера. Не обещай production verification без проверки.

## Интеграция с NORM pipeline

Завершённая пара — **input** для владельца контекста. Дальнейшая работа (отдельная задача): сверить с нормативными OpenSpec, обновить существующий `02_domain/services/<slug>.md`, синхронно обновить только релевантные `02_domain/registry` реестры, `services_map.md`, источники/статусы и запустить валидатор. Не добавлять PO-анкеты как конкурирующий бизнес-слой в `02_domain/registry`, не создавать `02_domain/services/<slug>_override.md`.
