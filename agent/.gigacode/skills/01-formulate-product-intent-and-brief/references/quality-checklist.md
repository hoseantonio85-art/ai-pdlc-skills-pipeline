# Quality gate для Product Task Brief

Используй этот чек-лист перед тем, как присвоить brief статус выше `DRAFT_REVIEW`.

## 1. Verdict

Выбери ровно один результат:

### `NEEDS_CLARIFICATION`

Критичные ответы ещё можно получить в рамках одной постановки.

### `NEEDS_DECOMPOSITION`

Задача содержит несколько независимых результатов или слишком велика для одного инкремента.

### `BLOCKED_BY_CONTEXT`

Критичный контекст отсутствует, устарел или противоречит сам себе, и product owner не может разрешить конфликт.

### `READY_FOR_UX`

Intent и Brief достаточно определены для UX. Для существующего продукта обязательный product context должен быть доступен; для явно автономной/greenfield инициативы `context_id: none` допустим по решению product owner.

## 2. Блокирующие критерии

Brief не готов, если хотя бы один пункт не выполнен.

- [ ] Проблема описывает реальную ситуацию, а не отсутствие экрана, кнопки или компонента.
- [ ] Основной пользователь определён.
- [ ] Понятен текущий сценарий или явно указано, что сценария ещё нет.
- [ ] Описаны последствия проблемы.
- [ ] Сформулирован ожидаемый результат без выбора UI-паттерна.
- [ ] Понятно, какой существующий сервис отвечает за результат, либо явно зафиксировано, что создаётся новый автономный сервис/продукт, либо конфликт обозначен.
- [ ] Scope ограничен.
- [ ] Критичные предположения не выданы за факты.
- [ ] Критичные противоречия источников разрешены либо brief имеет `BLOCKED_BY_CONTEXT`.
- [ ] Product owner явно подтвердил постановку.

## 3. Обязательные критерии качества

- [ ] Название отражает результат, а не интерфейс.
- [ ] Summary можно понять без истории чата.
- [ ] Указано, почему задача появилась.
- [ ] Цель описывает изменение для пользователя или продукта.
- [ ] User story содержит роль, результат и ценность.
- [ ] Гипотеза проверяема.
- [ ] Затронутые сервисы перечислены.
- [ ] Сущности не придуманы без основания.
- [ ] Известные бизнес-правила имеют источники.
- [ ] Out of scope защищает задачу от расползания.
- [ ] Ограничения имеют основания.
- [ ] Success criteria не содержат вымышленных чисел.
- [ ] Открытые вопросы имеют владельцев или явно помечены `owner TBD`.
- [ ] Перечислены использованные источники и их актуальность.
- [ ] Указан следующий этап.

## 4. Проверка на преждевременное решение

Найди в brief слова и конструкции:

- экран;
- модалка;
- drawer;
- таблица;
- карточка;
- кнопка;
- фильтр;
- вкладка;
- цвет;
- колонка;
- конкретный компонент UI Kit.

Для каждого использования определи:

1. это подтверждённое ограничение;
2. описание текущего интерфейса;
3. предложенная гипотеза;
4. преждевременно утверждённое решение.

Пункт 4 является блокером. Перенеси решение в раздел `Предложенная идея решения` и сформулируй требование через результат.

## 5. Проверка масштаба

Поставь `NEEDS_DECOMPOSITION`, если выполняются два или более признака:

- больше одной основной роли с разными целями;
- больше одного независимого пользовательского результата;
- больше одного самостоятельного процесса;
- затрагивается несколько сервисов, каждый меняет собственное поведение;
- невозможно сформулировать одну основную user story;
- success criteria относятся к разным проблемам;
- задача включает одновременно продуктовую фичу и крупную техническую миграцию;
- brief нельзя проверить одним связанным сценарием.

## 6. Проверка источников

- [ ] Каждый факт имеет источник либо явно указан как сообщение product owner.
- [ ] Файлы `needs-review` не используются как окончательное основание без оговорки.
- [ ] Не утверждается наличие релиза без записи в release-контексте.
- [ ] Не утверждается текущее поведение кода без проверки кодовой базы.
- [ ] Отсутствующий файл не пересказан так, будто был прочитан.
- [ ] Конфликты не скрыты.

## 7. Готовность напрямую к UX

Статус `READY_FOR_UX` допустим, если выполнен один из двух режимов.

### Existing product

- [ ] Подключён релевантный product context.
- [ ] Context provider/manifest доступны и реально прочитаны.
- [ ] Нет неизвестных product/domain rules, которые меняют flow.
- [ ] Нет критичных неизвестных прав, интеграций, переходов состояния или необратимых последствий.

### Autonomous / greenfield by explicit choice

- [ ] Product owner явно подтвердил, что инициатива не является изменением существующего продукта.
- [ ] `context_id: none` и `not-used-by-choice` зафиксированы.
- [ ] Intent, основной пользователь, outcome, scope, constraints и риски достаточны для UX.
- [ ] Неизвестные технические детали не подменены product rules и не блокируют пользовательский flow.

### Для обоих режимов

- [ ] Product owner разрешил переход в UX.
- [ ] Текущий/исходный и целевой сценарии понятны в необходимом объёме.
- [ ] UX-этап не будет вынужден самостоятельно придумывать критичную бизнес- или системную семантику.

Если для изменения существующего продукта обязательный контекст недоступен и это влияет на flow, используй `BLOCKED_BY_CONTEXT`. Не вводи локальный положительный статус, отсутствующий в `references/pipeline-status-contracts.md`.

## 8. Формат отчёта

```md
## Quality gate

**Verdict:** READY_FOR_UX

### Сильные стороны

- …

### Блокеры

- Нет.

### Существенные пробелы

- …

### Риски следующего этапа

- …

### Требуется подтверждение product owner

- проблема;
- целевой результат;
- scope;
- следующий этап.
```

Не используй числовой score: он может создавать ложную точность.


## 9. Проверка выбора контекста

- [ ] Контекст был выбран явно, определён project-level selector либо пользователь подтвердил работу без контекста.
- [ ] Не был молча выбран NORM только потому, что он чаще используется.
- [ ] Профиль ORM не был выдан за подключённый, если его status = `planned`.
- [ ] Provider действительно доступен.
- [ ] В brief зафиксированы context ID, provider, status и revision.
- [ ] При `context_id: none` подтверждено, что это осознанная автономная/greenfield инициатива; иначе existing-product задача требует контекста или `BLOCKED_BY_CONTEXT`.
