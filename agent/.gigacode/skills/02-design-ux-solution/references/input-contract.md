# Input Contract

## 1. Обязательный вход

Обязательный вход:

```text
00_intent.md
01_product_brief.md
```

`00_intent.md` должен содержать Intent, Why Now, тип, ожидаемое улучшение, критерии успеха, ограничения и риски. Используй его как outcome/priority guardrail, а не как источник UI-решений или детальных требований.

`01_product_brief.md` является подробным product truth для UX и должен содержать:

Минимально Brief должен содержать:

- task ID или понятное название;
- проблему;
- цель;
- основного пользователя;
- текущий сценарий или описание отсутствующего сценария;
- ожидаемый пользовательский результат;
- scope;
- out of scope;
- ограничения;
- открытые вопросы;
- использованные источники;
- статус.

## 2. Допустимые статусы

### `READY_FOR_UX`

Основной ready-status Stage 01. Можно начинать полный UX-этап.

Для existing-product задачи обязательный product context должен быть доступен. Для явно автономной/greenfield инициативы допустим `context_id: none`, если product owner разрешил прямой UX-handoff и ограничения режима без контекста зафиксированы.

### `DRAFT_*`

Разрешён только режим `explore`.

### `BLOCKED_BY_CONTEXT`

Не создавать финальное UX-решение.

### Статус отсутствует

Считать вход неподтверждённым. Уточнить у владельца или использовать режим `explore`.

## 3. Blockers входа

Остановить финальное проектирование, если неизвестно хотя бы одно:

- какая проблема решается;
- кто основной пользователь;
- какой результат должен получить пользователь;
- что входит в scope;
- какое решение или действие является центральным;
- какие критичные правила влияют на сценарий;
- существует ли конфликт между источниками, который меняет flow.
- согласованы ли Intent и Brief по outcome, scope и ограничениям.

Не продолжать финальное проектирование при отсутствии любого из двух артефактов. Не восстанавливать Intent задним числом из UX Solution.

## 4. Что можно уточнить на UX-этапе

Допустимо уточнять:

- точку входа;
- порядок действий;
- информационный приоритет;
- переходы;
- вспомогательные роли;
- состояния;
- edge cases;
- feedback;
- необходимость AI;
- выбор page/modal/drawer.

## 5. Что должно вернуться на анализ

Вернуть задачу на product/business/system analysis, если требуется определить:

- право пользователя на действие;
- юридически значимый статус;
- обязательное согласование;
- расчёт;
- доменный переход состояния;
- источник данных;
- API или интеграционный контракт;
- принадлежность сущности;
- ответственность сервиса;
- необратимое последствие.

UX не должен изобретать эти правила.
