# Design UX Solution

## Результат

Создай компактное UX Solution, которое объясняет предлагаемое поведение, причины решений и передаёт следующему этапу непротиворечивый сценарий. Не пересказывай Intent или Brief и не проектируй по привычному компоненту.

Обязательные task inputs: `00_intent.md` и `01_product_brief.md`. Intent определяет outcome, Why Now, приоритеты и guardrails; Brief определяет проблему, пользователей, scope, подтверждённые product rules и open questions. При конфликте не переписывай Intent молча: верни `NEEDS_PRODUCT_ALIGNMENT` и укажи расхождение.

## Обязательный context preflight

Возьми разрешённый контекст из Context trace Brief. Если trace неполон:

1. прочитай `context_id` из `<project>/.gigacode/product-context.yaml`;
2. открой `~/.gigacode/product-contexts.yaml`;
3. найди `contexts[context_id]`;
4. возьми `provider.root` и `provider.manifest`;
5. открой `<provider.root>/<provider.manifest>` и проверь `context_id`.

Открой профиль `for_ux_solution`, foundation, затронутые services, `03_ux/ux_principles.md`, релевантные части `03_ux/ux_patterns.md`, compact UI pattern registry и policy адаптации композиции, если они входят в профиль. Registry используй как карту проверенных product surfaces/pattern families, но не как запрет на новую UX-композицию. Pixel geometry, Visual DNA, HTML references и UI Kit API на UX-этапе не загружай. Полные Modal/Drawer authoring specs открывай только если выбор/вложенность surface реально требует их правил. Для NORM без manifest и профиля верни `BLOCKED_BY_CONTEXT`.

Если существующий pattern хорошо решает задачу — используй его как strong default. Если не решает, разрешено предложить `composition-adaptation` или `new-pattern-candidate`: укажи ближайший pattern, что из его semantics сохраняется, почему нужен deviation и какую пользовательскую проблему он решает. Не придумывай новую визуальную систему и не нарушай canonical surface behavior.

## Analytical specs: selective UX context

Analytical specs — on-demand evidence, а не обязательный payload. Если scope касается capability, для которого в `внешняя-спецификация-через-YAML` есть spec:

1. выбери только релевантные capability specs;
2. извлеки UX-significant facts: roles/permissions, lifecycle, states/actions, validation/business rules, async/error/retry behavior, object relationships и invariants;
3. не тащи в UX Solution API/DTO/DB/class/topic naming и implementation architecture;
4. статус `unknown` не превращай в абсолютную истину, `needs-review` требует дополнительного подтверждения;
5. если spec выявляет user-visible state/edge case, которого нет в Brief, включи его как подтверждённое domain constraint либо зафиксируй конфликт/open question;
6. analytical spec не имеет права менять Intent и не должен диктовать surface.

Цель — проверить UX на реальную доменную модель, не превратить UX Solution в техническую спецификацию.

## Процесс

1. Сформулируй UX-задачу, вход и критерий завершения.
2. Построй короткий journey и happy path.
3. Опиши только значимые альтернативы, ошибки и возвраты.
4. Проведи object and event check.
5. Расставь приоритет: сигнал → смысл → действие → детали → meta.
6. Выбери surfaces по намерению и обоснуй компромиссы. Для registry/monitoring page отдельно проверь, нужен ли situational overview/interactive analytics, чтобы пользователь понял ситуацию до чтения списка; если да, опиши aggregate question и связь с filters/drill-down.
7. Определи состояния, feedback, сохранение контекста и возврат.
8. Оцени роль ассистента.
9. Проведи consistency check.
10. Подготовь компактный structural handoff.

Каждое ключевое решение свяжи с пользовательской задачей, продуктовым источником или ограничением. Неподтверждённое решение обозначай как UX-гипотезу.

## Object and event check

До выбора интерфейса ответь:

- какие сущности являются устойчивыми объектами;
- что является событием, попыткой или версией;
- какие данные изменяются, а какие должны сохраняться;
- создаёт ли действие новый объект/событие или меняет существующее;
- нужна ли связь между исходным и новым объектом;
- важны ли история, аудит, воспроизводимость и доверие.

Не изменяй прошлое событие ради отображения нового процесса. Для журнала, истории попыток, аудита, запусков и версий повтор обычно создаёт новую запись с новым ID и ссылкой на исходную (`retry_of`, `previous_version` или эквивалент). Старую запись сохраняй. Если продуктовая семантика неясна и влияет на UX, верни `NEEDS_UX_DECISION`.

Не превращай раздел в схему API: фиксируй только сущности, состояния и связи, влияющие на пользовательское решение.

## Роль ассистента

Проверь ассистента в основном и проблемных сценариях. Включай его, если он помогает объяснить данные или ошибку, найти объект, подготовить действие либо сократить сложный путь. Не добавляй декоративно и не заменяй им навигацию, статусы и явные действия.

Для валидного сценария укажи: момент, намерение, доступный контекст, ответ/действие, подтверждение человеком и fallback. Если ассистент не нужен, достаточно одной причины. Используй только один раздел про ассистента.

## Выбор surfaces

- Page — самостоятельная работа, обзор или устойчивый контекст.
- Card registry/row-cards — множество объектов с приоритетом, объяснением и действием.
- Dashboard — агрегаты для мониторинга и перехода к зонам внимания.
- Object Modal — самостоятельный объект без потери исходного множества; может быть большой.
- Drawer — зависимая задача, фильтры, настройка, выбор или дополнительный слой.
- Inline/expand — короткая локальная деталь или действие.

Классическую таблицу не используй как основной реестр NORM. Drawer, Modal и Page выбирай по зависимости задачи и дальнейшим действиям, а не по произвольному размеру.

## Consistency check

Перед статусом готовности проверь:

- happy path достигает цели brief;
- альтернативы используют ту же объектную модель;
- действия не уничтожают историю и не меняют прошлые факты;
- статусы, переходы, тексты и feedback согласованы;
- навигация соответствует заявленной архитектуре;
- роль ассистента не дублирует основной интерфейс;
- handoff не противоречит rationale и acceptance criteria;
- открытые вопросы не замаскированы предположениями.

## Формат результата

Используй `references/ux-solution-template.md`. Не добавляй дублирующие разделы. Journey и handoff оформляй компактными блоками, не большими Markdown-таблицами. Обычно укладывайся в 1600–2200 слов.

Structural handoff для каждой surface содержит только: назначение, вход, главный сигнал, действия, состояния, переход/возврат и сохраняемый контекст. Не задавай цвета, пиксели, API и конкретные компоненты UI Kit.

## Quality gate

Статус `READY_FOR_PROTOTYPE` допустим, если для выбранного product context прочитан manifest и профиль; для явно автономной/greenfield инициативы с `context_id: none` — если отсутствие product context зафиксировано и не требует выдумывать существующие product/domain rules. В обоих режимах объектная логика должна быть определена, сценарии непротиворечивы, история не теряется, ключевые решения обоснованы, роль ассистента оценена, а handoff позволяет собрать прототип без догадок.

Используй статусы:

- `READY_FOR_PROTOTYPE` — решение готово;
- `NEEDS_UX_DECISION` — не определена критичная продуктовая или объектная семантика;
- `NEEDS_PRODUCT_ALIGNMENT` — Intent и Brief расходятся по outcome, scope или guardrails;
- `BLOCKED_BY_CONTEXT` — недоступен обязательный продуктовый источник.
