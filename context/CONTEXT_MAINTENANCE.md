# Поддержка единого продуктового контекста NORM

## Принцип

Контекст хранится один — `product-system/`. Нет наложений, параллельных бизнес-слоёв или конкурирующих каталогов. Файлы `02_domain/services` (описания) и `02_domain/registry` (быстрые структурные индексы) должны быть **синхронны**. Исходный OpenSpec подключается отдельно через разрешённый YAML и проверяется по фактическому состоянию; это потенциальный первоисточник, а не отдельная доменная модель.

## Специальный источник AS IS для «Мер»

Выполненная 23.10.2026 проверка снимков frontend/backend зафиксирована в единственном `product-system/02_domain/services/measures.md` с реестром вопросов `product-system/02_domain/registry/measures_questions.md`. Для текущего поведения мер она приоритетнее исторического OpenSpec. Это **локальное** правило; оно не изменяет модель обновления иных сервисов, не означает подтверждения production и не подключает репозитории как live sources. При последующей проверке новых версий кода обновлять эти два документа и навигационные метаданные согласованно.

## Обновление существующего сервиса

1. Получить новый снимок OpenSpec со стабильной ревизией; сравнить с зарегистрированным `[редакция исходника удалена]`.
2. Определить изменения правил, сущностей, статусов, ролей, лимитов, связей и бизнес-процессов.
3. Исправить **существующий** документ `product-system/02_domain/services/<service>.md` (не добавлять override); новые сервисы добавлять туда же.
4. Синхронно поправить `services_map.md`, `service_registry.yaml`, `capability_registry.yaml`, `role_registry.yaml`, `common_business_rules.md`, `glossary.md`, `known_constraints.md`, source registry и статус по scope изменений.
5. При необходимости обновить внешний репозиторий первичных спецификаций по утверждённой процедуре и уточнить ссылки/версии в локальном YAML; исходники не копировать в этот пакет. Неподтверждённый конфликт отразить в соответствующем существующем документе, а не в overlay.
6. Запустить `python -X utf8 tools/validate_context.py --write-report`, сверить refs, role/service/capability ID и убедиться в отсутствии неожиданных изменений по `git diff` (файловый manifest исторических ZIP-сборок больше не распространяется).

## Что нельзя трогать автоматически

- UI-компоненты, дизайн-систему, UX/UI-паттерны, связи скиллов/агентов и stage contracts только из-за изменения бизнес-спеки;
- выпуск фич в production — без release/runtime evidence;
- API/DTO/storage в Product SDD вместо бизнес-описания.

## Границы других источников

`01_foundation/` — продуктовые принципы; `03_ux/` и `04_ui/` — UX/UI правила и прототипы; аналитические спецификации подключаются как внешние источники (в архиве отсутствуют). При бизнес-противоречии с каноническим OpenSpec приоритет имеет OpenSpec. UI Kit package/types остаётся истиной технического UI API.

## Производственные и технические источники

Не копировать полные frontend/backend репозитории в контекст. Target repo на этапе frontend — реализационная истина. Новые product facts из OpenSpec обновляют единый контекст независимо от наличия актуальных production screenshots.

## Версионирование

Актуализировать источник/revision в source registry и индексе. Изменения бизнеса внутри данного дистрибутива — синхронизация контекстных знаний без смены публичных API/manifest schema или имен скиллов. Если меняется routing/schema — выпускать отдельно версию пайплайна после интеграционного QA.

## Размещение и проверка

Текущая рабочая структура репозитория: `agent/.gigacode/{skills,agents}` + отдельный `context/`. Установка, маршруты provider/selector и первый запуск — в корневом `README.md`. Контекстный validator ищет GigaCode-настройки в `../agent/.gigacode/`, но также допускает автономный `context/` без соседних скиллов. Отчёт `CONTEXT_VALIDATION.json` создаётся только по явному `--write-report`, а не хранится как версия рабочей истины.
