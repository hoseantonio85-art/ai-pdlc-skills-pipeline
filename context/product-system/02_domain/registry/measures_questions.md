# NORM — Меры: открытые вопросы, расхождения и история решений

> **Исторический реестр вопросов Q/R.** Все решения и открытые противоречия сохранены для продолжения работы; техническая трассировка исключена. Не считать доказанным нынешний production.

**Редакция:** 2.0 · 23.10.2026  
**Составлено вместе с:** [`../services/measures.md`](../services/measures.md)  
**Назначение:** передать профильным PO, методологу и разработчикам нерешённые вопросы **по результатам предыдущего исследования frontend и backend (исходники здесь не поставляются)**, не потеряв прежние решения и не заставляя повторно исследовать уже установленные факты.

> **Правило работы:** текущую модель AS IS описываем **по историческим выводам предыдущего исследования кода, которые требуют повторной проверки**. «Код подтверждает» значит только «есть в предоставленном снимке», а не «проверено в production». Если прежнее бизнес-решение противоречит коду, код описывает AS IS, а решение переносится в **открытое расхождение**. Нельзя автоматически превращать пожелание в действующий валидатор. Статус «технически выяснено» не означает «методологически согласовано».

## 1. Как пользоваться этим реестром

- **П0 — блокирующее расхождение / высокое влияние** на UX, требования и качество данных. Желательно разбирать первым с владельцем предметной области и командой.
- **П1 — существенно для полноты сервиса**, но можно использовать описанную модель, пометив границу.
- **П2 — локальная особенность / последующая проверка**, не блокирует типовые сценарии.
- **Код выяснил** — технический ответ есть; дополнительная проверка может понадобиться лишь для бизнес-смысла или production.
- **Частично** — техническая часть известна, существенная часть зависит от внешних модулей, прав или методики.
- **Открыто** — изученных двух репозиториев недостаточно.
- **Конфликт с прежним решением** — AS IS установлен по коду, но принятую ранее цель нужно либо отменить, либо оформить как изменение.

## 2. Открытые вопросы и технические ответы (сохраняем ID Q-01–Q-28)

### 2.1. Приоритет П0 — согласовать бизнес-правило или интеграцию

#### Q-05. Обязательность прямой связи с риском

- **Состояние:** **Конфликт с прежним решением**.
- **Прежний ответ:** по БТ и договорённости владельца контекста — у каждой меры должен быть хотя бы один *прямой* связанный риск, включая меру из события; см. R-05.
- **Что делает код:** `isLinkExist` считает условие выполненным, если есть **хотя бы одна связь типа `incidentToMeasure` ИЛИ `riskToMeasure`**. Эта проверка запускается при предусмотренных workflow-действиях через профиль `workflowRequiredLink` **только если `isSuorPlan=false`**. Для меры плана развития СУОР эта проверка не применяется.
- **Нужно решить:** бизнес хочет ужесточить реализацию до «всегда прямой риск» либо принимает текущую альтернативу «риск или событие»? Является ли исключение для плана СУОР осознанным?
- **Кому:** PO «Меры», PO «Риски», методолог; затем backend lead.
- **Подтверждение:** ссылки на исходники исключены; проверить в рабочем окружении.
- **До ответа:** **AS IS: риск или событие, исключение СУОР**. Нельзя требовать прямой риск в интерфейсе только потому, что он был в БТ.

#### Q-06. Автоматическое наследование риска события при создании меры

- **Состояние:** **Открыто для end-to-end интеграции**.
- **Прежний ответ:** владелец контекста решил, что новая мера из события должна автоматически получить связь с риском события; R-06.
- **Что делает видимый код:** `CreateMeasureView` принимает `linkType` и `linkId` из URL и после сохранения создаёт **одну соответствующую связь**. Обнаруженный backend `CreateLinks` создаёт переданные связи; в этих двух репозиториях дополнительный запрос «узнать риск события и создать `riskToMeasure`» не обнаружен.
- **Нужно проверить:** может ли вызов из микрофронта «События» заранее передавать/создавать прямую связь? Делает ли это link-service? Если нет — отменяем обещание AS IS или оформляем новую фичу. Что делать, если событие не связано с риском?
- **Кому:** frontend/backend «События», владелец link-service, PO «Меры».
- **Подтверждение:** ссылки на исходники исключены; проверить в рабочем окружении.
- **До ответа:** **AS IS: создаётся переданная связь с событием**; наследование отдельного прямого риска не объявлять установленным.

#### Q-02. Какие фактические поля действительно обязательны на согласовании завершения

- **Состояние:** **Частично, расхождение БТ и валидации**.
- **БТ:** требует отчёт о реализации, фактическую стоимость и старое поле эффективности; файлы необязательны.
- **Что делает код:** `actualDate` имеет `notNull` и `dateInPast` под профилем `implemented`; `report` — `textarea` с ограничением 4000 символов **без явно указанного `notNull`**; `actualValue` — числовое поле **без явно указанного `notNull`**; `efficiency` — `visible: never`, `editable: false`. Нужна проверка, не добавляет ли правила общая библиотека.
- **Нужно решить:** обязателен ли *текстовый* отчёт, обязательно ли указывать фактический бюджет, допускаются ли нулевые/отсутствующие затраты и отличается ли проверка для уже выполненной при создании меры?
- **Кому:** PO, разработчик валидации и QA; при необходимости методолог.
- **Подтверждение:** ссылки на исходники исключены; проверить в рабочем окружении.
- **До ответа:** считать гарантированно явной в YAML проверку **фактической даты**, а не документа/бюджета. **Отчёт — это текстовое поле, не файл.**

| R-12 | Уже выполненная минует обычный запуск и идёт на согласование результата | **Сохраняем с уточнением:** это отдельная ветка согласования, названия UI могут отличаться |
| R-13 | До согласования — удалить; после начала — отклонить | **Сохраняем по бизнес-смыслу**, код допускает удаление и в некоторых ветках доработки |
| R-14 | История существует | **Подтверждено кодом** |
| R-15 | Видимая точка истории — итог изменений за этап | **Подтверждено кодом в пределах process history**; не отрицать внутренние сохранения |
| R-16 | История: автор, действие, время, комментарий | **Подтверждено FE**; также видны дельты полей и связей |
| R-17 | Отчёт — текстовое поле, а не вложение | **Подтверждено YAML** (`report: textarea`) |
| R-18 | Вложения необязательны по БТ | **Сохраняем;** явной обязательности файлов в рассмотренном YAML нет; вопрос отчёта/бюджета — Q-02 |
| R-19 | Фактическую дату вводят вручную | **Подтверждено как редактируемое поле**; техническая дата завершения — отдельный вопрос Q-15 |
| R-20 | Развёрнутый модуль прогнозной/фактической эффективности не реализован | **Сохраняем**, UI не найден, старый `efficiency` скрыт |
| R-21 | Системные меры и меры плана развития СУОР существуют | **Подтверждено двумя полями**, значения терминов неизвестны (Q-10, Q-11) |
| R-22 | Системные меры участвуют в оценке зрелости | **Документировано руководством**, точная формула не проверена (Q-12) |
| **R-23** | В БТ аналитическая «Истекает срок» — 14 дней | **Не считать текущим UI-порогом**: в коде `soonRealizationDays=21`, уведомления 30/7; Q-13 |
| R-24 | Отметка выполнения и подтверждение завершения — два действия | **Подтверждено workflow** |
| R-25 | Причины задержек часто обсуждаются вне NORM | **Сохраняем как описание практики**, встроенный чат мер не найден |
| R-26 | РМ может быть автором | **Подтверждено RM-маршрутом**; матрица самосогласования уточняется по Q-04 |
| R-27 | «Входит в план развития СУОР» — признак, не документ | **Подтверждено** `isSuorPlan: Boolean` |

## 4. Расхождения требований и кода, требующие отдельного решения

| Тема | По исходникам (AS IS данного среза) | Что говорили раньше / что в БТ | Рекомендованное действие |
|---|---|---|---|
| Прямая связь с риском | **Риск ИЛИ событие**, у СУОР-плана исключение | **Хотя бы один риск** для каждой меры | Q-05: принять код или постановка на изменение |
| Наследование риска из события | FE создаёт **переданную** связь, прямую вторую не создаёт в видимой цепочке | Принято «подхватывает риск события» | Q-06: проверить внешний код, затем решение |
| Текстовый отчёт/фактический бюджет | Нет явных `notNull`; дата реализованной меры обязательна | По БТ отчёт и фактическая стоимость обязательны | Q-02: решить, нужен ли валидатор |
| Порог «скоро» | `soonRealizationDays=21` | 14 дней для карточки аналитики в БТ; в беседе упоминались 7 дней | Q-13: развести три механизма; 7 не принимать как UI-порог |
| Модуль эффективности | Нет активного пользовательского UI; старый `efficiency` скрыт | Подробное задание на расчёт из БТ | **Не реализовано**; не добавлять в AS IS |
| Автоудаление черновика | В изученном backend не найдено | В БТ описан таймер/письма | Q-19: проверить внешний планировщик, не считать функцией без проверки |
| Сводная аналитика/экспорт | В MFE мер реестр и фильтры, нет целого БТ-дашборда | В БТ сравнение месяца/прогресс, в руководстве есть отдельная аналитика | Q-20: проверить сервис аналитики |
| Системные/СУОР после завершения | `verification` РП, ветки уточнения | Руководство только упоминает иной процесс | Q-01: согласовать **критерии**, а не искать второй раз маршрут |
| Фактическая дата | `actualDate`, вводимое поле | Старый БТ местами говорит об автозаполнении при финале | Зафиксировать ручной ввод; отдельно Q-15 для времени закрытия workflow |

## 6. Как закрывать вопросы и обновлять контекст

1. Отвечающий фиксирует **ID вопроса, дату, решение, источник (методика/задача/код/production), сферу применения и владельца**. При противоречии исходному коду отдельно указывает: меняем продукт или обновляем знание о работе текущей версии.
2. **AS IS в `01_...FINAL.md` меняется только при новом подтверждении фактического поведения**. Пожелания оформляются отдельным Intent/задачей и не помечаются доступными сейчас.
3. Закрытый ID не удаляется, а переводится в «решено» с кратким основанием. Не нужно задавать тот же вопрос заново, если ответ есть и не обнаружено нового противоречия.
4. После актуализации основного описания обновить `02_domain/services/measures.md`, затем производные реестры `02_domain/registry`, а не вести две независимые версии предметной модели.
5. Для будущего диалогового skill это обязательные принципы: **не угадывать**, сохранять source of truth и версии, разделять бизнес-понятие и техническую реализацию, автоматически формировать такой реестр и выдавать PO только вопросы, ответы на которые нельзя извлечь из предоставленных источников.
