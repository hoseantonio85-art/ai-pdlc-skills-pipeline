> **Режим без встроенных технических спецификаций:** приведённая ниже иерархия описывает приоритет доказательств, **если они реально подключены**. Без проверенных исходных спецификаций использовать только локальную нормализованную модель, отмечая её исторический статус, и не выдавать её за актуальную production-схему.

# Источники истины для единого контекста NORM

## Приоритеты

1. **Предметные бизнес-правила существующих сервисов:** исходные OpenSpec (`внешняя-спецификация-через-YAML`, снимок `[редакция исходника удалена]`) — нормативный первоисточник. Спецификации зафиксированы в том числе для лимитной кампании, рисков, событий, мер, AI-агентов, продуктов, контрагентов и административных функций.
2. **Единая читаемая модель NORM:** `02_services/` и `07_business_context/` — синхронно поддерживаемое изложение этих OpenSpec, а не альтернативный набор требований. При несоответствии исправить модель после проверки оригинального spec и его версии.
3. **Продуктовые принципы:** `01_product_foundation/` определяет цель продукта и философию; не меняет точные доменные требования OpenSpec.
4. **Task artifacts:** согласованные Intent/Brief/UX/SDD задают границы **новой** задачи, но не должны без явно оформленного изменения изменять модель существующего сервиса. Изменения требований должны отражаться в обновлённой OpenSpec и едином контексте.
5. **UX/UI:** `03_ux/`, `04_ui/` — нормативны для паттернов и реализации интерфейса; не подменяют серверные состояния, права, расчёты или API.
6. **UI Kit API:** установленный пакет и types являются истиной для компонентов, props и enums; иные описания уступают фактическим объявлениям той же версии.
7. **Frontend engineering:** реальный target repo — источник истины о техническом runtime/архитектуре.

## Локальное исключение: сервис `measures`, описание AS IS (срез 23.10.2026)

Для вопросов о **текущей реализации сервиса «Меры»** в проверенных снимках `external-product-frontend` и `external-product-backend` приоритет имеют сведения `[CODE]`, описанные в [`02_services/measures.md`](../02_services/measures.md). Исходники проверялись вне этого дистрибутива; их наличие в `source_registry.yaml` **не означает подключения живых репозиториев или подтверждения production**. БТ, руководство и OpenSpec остаются нормативными/историческими источниками требований; обнаруженные расхождения внесены в [`measures_questions.md`](measures_questions.md), их нельзя молча считать реализованными или автоматически «исправлять» в коде.

**Обязательное чтение для затронутого сервиса:** если задача касается создания, согласования, реализации, связей, сроков, истории, прав или форм меры, откройте `service_registry.yaml` → `measures.primary_document` → релевантные разделы **полного** `measures.md` **до** генерации продуктовых требований/UX/прототипа. Для неразрешённых случаев прочитайте `measures_questions.md`. Чтения одной строки из service/capability registry недостаточно. Для остальных сервисов приоритет OpenSpec остаётся прежним. Изменение контрактов/целевого поведения — отдельное решение PO, а не вывод из AS IS-кода.

## Точность статусов

**Существующий сервис со спецификацией** — допустимая бизнес-фактическая модель. **Специфицированное требование** — нормативное поведение и сценарий. **Развёрнутая production-фича** — отдельное утверждение, требующее release/runtime evidence. Их нельзя смешивать.

Не утверждать, что спецификации устарели только из-за отсутствия второго источника; для текущей модели они определены владельцем продукта как source of truth. Полноту исторических/новейших изменений удостоверяет ревизия `[редакция исходника удалена]`. Частичные OpenSpec для ассистента/мониторинга не расширять догадками.

## Правило обновления

Новая или обновлённая OpenSpec → выявить изменения сервиса/контракта → обновить **те же** `02_services/` и `07_business_context/` → согласовать связи/правила/роли → валидация. Внешние OpenSpec не упакованы, их версию и доступность требуется проверять через YAML. Не создавать `overlay`, `spec-derived` или конкурирующую доменную модель.
