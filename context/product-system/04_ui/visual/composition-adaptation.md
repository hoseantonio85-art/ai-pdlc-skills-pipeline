# Composition adaptation policy

## Назначение

Паттерны NORM помогают сохранять узнаваемость продукта и проверенные способы взаимодействия, но не являются каталогом жёстких экранных шаблонов. Агент должен уметь применять существующее, адаптировать композицию под задачу и предлагать новое решение, если текущие паттерны не решают пользовательскую задачу достаточно хорошо.

## Три уровня обязательности

### 1. Invariants — обязательные контракты

Не менять без отдельного продуктового решения:

- роль surface: Page / Object Modal / Drawer / regular Modal / inline;
- сохранение и возврат пользовательского контекста;
- Object View: object-level actions находятся в правой action/meta zone, общий Footer отсутствует;
- Object Create/Edit: commit actions находятся в fixed Footer;
- canonical Modal/Drawer shell behavior, stack, close/back и dirty-state semantics;
- UI Kit/tokens, базовая продуктовая типографика, цветовая семантика и accessibility;
- подтверждённые product/business rules и состояния сценария.

Это контракт поведения и системы, а не точная схема каждого блока.

### 2. Strong defaults — проверенные композиции

Использовать как предпочтительную отправную точку, если они соответствуют задаче:

- card registry / entity cards;
- registry page controls;
- quick filters + on-demand search + advanced filter drawer;
- main content + right action/meta zone для Object View;
- situational overview / interactive analytics, когда агрегаты помогают понять ситуацию;
- floating create/chat surface только когда требуется постоянное следующее действие.

Разрешено:

- менять порядок optional sections;
- объединять или разделять смысловые блоки;
- выбирать другую плотность и количество колонок в пределах visual DNA;
- заменять конкретный вид визуализации на более подходящий данным;
- добавлять новый промежуточный блок, если он сокращает путь к решению;
- исключать optional pattern, если он не даёт ценности в конкретном сценарии.

### 3. References — визуальные ориентиры

HTML reference scenes, screenshots и production examples показывают характер продукта: пропорции, плотность, hierarchy, rhythm, surfaces и interaction feel.

Они НЕ являются:

- обязательным DOM;
- готовым React API;
- запретом на новую композицию;
- требованием копировать один экран во все сервисы;
- доказательством, что каждая деталь production UI является canonical.

## Когда можно предложить новую композицию

Новая композиция допустима и ожидаема, если выполняется хотя бы одно условие:

1. существующий pattern не покрывает ключевую пользовательскую задачу;
2. форма данных требует другого способа сравнения или исследования;
3. существующая композиция создаёт лишние шаги, перегружает экран или скрывает приоритет;
4. новый сценарий вводит новый тип объекта, анализа или взаимодействия;
5. предложенное решение явно улучшает понимание ситуации или путь к действию.

Перед предложением нового решения агент должен:

1. назвать ближайшие существующие patterns и что из них сохраняется;
2. указать, что именно не подходит;
3. сохранить invariants, product visual DNA и UI Kit semantics;
4. объяснить пользовательскую пользу изменения;
5. пометить решение как `composition-adaptation` или `new-pattern-candidate` в handoff.

Не создавать новизну ради визуального разнообразия.

## Как новая композиция становится паттерном

Один удачный экран не создаёт новый canonical pattern автоматически.

Новая композиция сначала является task-level решением. После проверки она может стать `pattern candidate`. Для нормализации нужны повторяемость, evidence из нескольких сценариев/сервисов либо отдельное решение владельца системы.

## Короткое правило для AI

> Existing pattern = strong default, not a cage. Preserve product invariants; adapt composition when the task benefits; explain deviations; do not invent a new visual language.
