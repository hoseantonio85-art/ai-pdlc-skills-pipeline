# Drawer — паттерн и компонент

## Актуальный нормативный слой — решения владельца (приоритет выше разделов ниже)

Этот раздел обновляет старую общую спецификацию **без удаления её подробной анатомии, примеров, состояний и QA-сценариев**. При противоречии актуальный слой имеет приоритет; численные значения из старой части рассматриваются как исторические референсы, а не обязательные новые API.

### Общая модель

- **Единый Drawer** с независимыми осями `theme = NORM | ORM`, `scope = viewport | container`, `size = S | M | L | XL`, стеком слоёв и необязательной навигацией между соседними объектами. Уточняющие параметры — концептуальные, **не подтверждение публичного API UI Kit**.
- Пресеты ширины: **S 608, M 720, L 840, XL 1184 px**. Выбор определяется задачей и содержимым, без произвольных ширин.
- `viewport` может перекрывать родительскую Modal; `container` помещается в её область и перекрывает Header/Body/Footer.
- Каждый **новый** Drawer имеет собственный overlay. `Close` закрывает **только верхний** Drawer, не уничтожая состояние нижних. Строгого ограничения в два слоя нет.
- **NORM:** поверхность со скруглением со всех сторон, Close внутри Header; следующий слой той же ширины или на один предустановленный размер меньше. Обычно достаточно до трёх Drawer; четыре и более — только с явным UX-обоснованием, жёсткого запрета нет.
- **ORM:** поверхность, пристыкованная к правому краю, Close снаружи поверхности как часть композиции; новые слои одинаковой ширины. Допускается вертикальная навигация по соседям в упорядоченной коллекции; после трёх слоёв нужна особая проверка читаемости и состояния.
- Нельзя открывать отдельный Drawer на каждый шаг одной формы. Редактирование текущего объекта может происходить в том же Drawer.
- Escape **выключен по умолчанию** для Drawer; его включение требует отдельного утверждения сценария. Если разрешён, воздействует только на верхний слой. Поведение обычной Modal определяется её собственным контрактом.
- `Back` и `replace content` **не утверждены как обязательное поведение**: не добавлять их автоматически. Навигация к соседнему объекту отличается от `Back` и от стека слоёв.
- Header фиксирован, Body — единственная основная область скролла, Footer закрепляется только для глобальных действий и может отсутствовать.
- Открытые вопросы, **не выдавать за решённые**: click-away по overlay, dirty guard, responsive geometry, точные токены header/status, Back/replace, focus/ARIA/motion, совокупная прозрачность scrim.

### Что из старой спецификации больше не является обязательным

Любые старые формулировки `closeOnEscape: true`, «Escape всегда закрывает Drawer», обязательность Back при замене содержимого, максимум два Drawer, фиксированные 32 px padding / 24 px radius / 44 px кнопки, универсальные layout-токены или технический интерфейс props из примеров ниже — **исторические иллюстрации**, а не утверждённый контракт NORM и ORM. Фактические prop names и focus/stack API требуется проверить в подключённом компоненте или целевом repo.

## 1. Назначение документа

Документ описывает единые правила проектирования, использования и реализации Drawer в продуктовой системе **UI Kit AI PDLC Ready**.

Он нужен:

- дизайнерам — чтобы выбирать Drawer осознанно и не создавать новые локальные варианты;
- аналитикам и product owners — чтобы понимать роль Drawer в пользовательском сценарии;
- разработчикам — чтобы реализовывать одинаковое поведение во всех продуктах;
- AI-агентам — чтобы генерировать интерфейсы без произвольных ширин, крестиков, вложенностей и схем действий.

Документ является контрактом для двух продуктов:

- внутренней системы управления операционными рисками;
- коммерческого SaaS-продукта управления операционными рисками.

Бизнес-процессы продуктов могут отличаться. Геометрия, анатомия и базовое поведение Drawer должны быть общими.

---

# 2. Определение

**Drawer** — блокирующая боковая поверхность, которая открывается поверх текущего интерфейса и позволяет выполнить подчинённую задачу без перехода на другую страницу и без потери родительского контекста.

После закрытия пользователь возвращается в исходное состояние:

- к той же странице, модалке или Drawer;
- с сохранёнными введёнными данными;
- с сохранённой прокруткой;
- с сохранённым выбором;
- к элементу, из которого Drawer был открыт.

## Ключевая формула

> Page = самостоятельная рабочая область.  
> Modal = основной фокус, объект или важное решение.  
> Drawer = подчинённая задача без потери контекста.

Drawer определяется не размером и не количеством контента, а ролью задачи в сценарии.

---

# 3. Место Drawer в системе слоёв

Интерфейс может раскрываться слоями:

```txt
Page
├─ Modal
│  ├─ Contained Drawer
│  └─ Viewport Drawer
└─ Viewport Drawer
   ├─ Replace content
   └─ Second Drawer
```

Drawer может открываться:

- поверх страницы;
- внутри модалки;
- поверх модалки;
- поверх другого Drawer;
- с заменой собственного содержимого без создания нового слоя.

Только верхний слой активен. Все нижележащие поверхности сохраняют состояние, но блокируются.

---

# 4. Когда использовать Drawer

Использовать Drawer, когда пользователь должен выполнить дополнительную задачу, а родительский контекст важно сохранить.

Подходящие сценарии:

- расширенный фильтр;
- выбор связанного объекта;
- просмотр истории;
- просмотр версии;
- просмотр источника или доказательства;
- уточнение данных;
- комментарий;
- настройка параметров;
- короткое или среднее редактирование;
- добавление связанной сущности;
- preview связанного объекта;
- служебная информация;
- технические детали;
- дополнительный шаг формы;
- локальная вспомогательная работа внутри модалки;
- работа с AI-объяснением или источниками, если это вторичный слой;
- спор, комментарий или предложение изменения оценки;
- вспомогательный рабочий сценарий, после которого пользователь возвращается к основному объекту.

Drawer может быть длинным и содержательно сложным. Это допустимо, если его задача остаётся подчинённой родительскому контексту.

---

# 5. Когда не использовать Drawer

Не использовать Drawer, если:

- открывается основной объект страницы для полноценного изучения;
- пользователь начинает самостоятельный раздел работы;
- новой поверхности нужен собственный URL;
- требуется постоянное одновременное взаимодействие с основной страницей;
- действие является простым подтверждением и помещается в dialog или popover;
- задача требует сложной навигации между несколькими самостоятельными разделами;
- после завершения пользователь не должен возвращаться к родительскому контексту;
- Drawer используется как постоянная боковая панель;
- для каждого шага формы создаётся новый слой;
- вложенность превышает допустимый стек;
- ширина создаётся специально под один макет.

Для основного объекта использовать Modal или Page.

Для постоянной боковой области использовать Side panel.

Для короткого подтверждения использовать Dialog или Popover.

---

# 6. Drawer, Modal, Page и Side panel

| Контейнер | Роль | Блокирует контекст | Сохраняет контекст | Типичный сценарий |
|---|---|---:|---:|---|
| Page | Самостоятельная работа | Нет | Не требуется | Раздел, реестр, рабочее пространство |
| Modal | Основной фокус и решение | Да | Да | Просмотр объекта, принятие решения |
| Drawer | Подчинённая задача | Да | Да | История, фильтр, выбор, уточнение |
| Side panel | Постоянная соседняя область | Обычно нет | Да | Инспектор, постоянно доступные параметры |
| Dialog | Короткое подтверждение | Да | Да | Подтвердить, отменить, удалить |
| Popover | Локальное компактное действие | Нет или локально | Да | Меню, подсказка, простая настройка |

# 7. Варианты размещения

Компонент один. Область размещения задаётся свойством `scope`.

```ts
type DrawerScope = 'viewport' | 'container';
```

## 7.1. Viewport Drawer

Drawer открывается от правого края viewport.

Используется:

- поверх страницы;
- поверх модалки, когда новая задача должна перекрыть всю рабочую область;
- поверх другого Drawer;
- для самостоятельной связанной сущности;
- для широкого рабочего Drawer.

Поведение:

- занимает всю доступную высоту viewport;
- scrim покрывает весь viewport;
- блокирует все нижележащие слои;
- не ограничивается границами родительской модалки;
- закрывается независимо;
- состояние нижнего слоя сохраняется.

## 7.2. Contained Drawer

Drawer открывается внутри родительского контейнера, обычно внутри Modal.

Используется для локальной задачи, связанной только с содержимым родительской Modal.

Поведение:

- остаётся внутри границ Modal;
- не выходит за её скругления;
- открывается от правого края Modal;
- **перекрывает Header, Body и Footer родительской Modal целиком**;
- локальный scrim покрывает всю Modal;
- страница под Modal продолжает блокироваться самой Modal;
- Modal сохраняет состояние;
- взаимодействие с Modal недоступно, пока открыт Drawer;
- после закрытия пользователь возвращается в ту же точку Modal.

Contained Drawer — не отдельный компонент. Это `Drawer` со значением `scope="container"`.

## 7.3. Выбор области

Использовать `container`, если задача:

- относится только к текущей Modal;
- должна визуально оставаться внутри неё;
- не должна перекрывать весь viewport;
- после закрытия возвращает пользователя к незавершённой работе в Modal.

Использовать `viewport`, если:

- открывается самостоятельная связанная сущность;
- требуется больше пространства;
- новый слой не должен зависеть от геометрии Modal;
- Drawer открывается поверх страницы или другого Drawer;
- локальный Drawer внутри Modal стал слишком большим или сложным.

# 8. Размеры

В системе используются только четыре размера.

```ts
type DrawerSize = 'S' | 'M' | 'L' | 'XL';
```

| Размер | Базовая ширина | Основные сценарии |
|---|---:|---|
| S | 608 px | Фильтры, комментарии, простые настройки, короткие формы |
| M | 720 px | История, стандартное редактирование, детали, выбор сущности |
| L | 840 px | Сложная форма, несколько секций, две колонки, большой список |
| XL | 1184 px | Редкое широкое рабочее пространство, аналитика, сложная композиция |

## 8.1. Правила выбора размера

Выбирать размер по структуре задачи, а не по длине конкретного текста.

### S — 608 px

Использовать для:

- расширенного фильтра;
- комментария;
- небольшой формы;
- настройки;
- простого выбора;
- короткого подтверждаемого действия;
- одной колонки с небольшим количеством секций.

### M — 720 px

Использовать для:

- истории изменений;
- средней формы;
- редактирования объекта;
- выбора связанной сущности;
- просмотра источников;
- деталей с несколькими смысловыми блоками;
- большинства стандартных Drawer.

M — размер по умолчанию, если S явно тесен, а L не обоснован.

### L — 840 px

Использовать для:

- сложной формы;
- нескольких крупных секций;
- двухколоночной композиции;
- списка с расширенными карточками;
- детального review;
- сценария с большим количеством метаданных.

### XL — 1184 px

Использовать редко:

- для широкой аналитики;
- для сложной композиции;
- для большого рабочего содержимого;
- когда L объективно не позволяет выполнить задачу.

Если XL начинает использоваться регулярно, нужно проверить, не должен ли сценарий стать Modal или Page.

## 8.2. Запрещено

- произвольная ширина;
- отдельный размер под конкретную форму;
- ширины 550, 607, 630, 742, 834, 850 и другие локальные значения;
- изменение ширины при переходе между уровнями одного сценария;
- автоматическое увеличение Drawer из-за длинного текста;
- создание `XXL`, `Wide`, `Custom` без системного решения.

## 8.3. Миграция существующих ширин

| Legacy width | Новый размер |
|---:|---|
| 550 px | S |
| 607 px | S |
| 630 px | S |
| 720 px | M |
| 742 px | M |
| 834 px | L |
| 850 px | L |
| 1180 px | XL |

# 9. Адаптивность

Desktop-проверка выполняется на ширине viewport около `1366 px`.

Ширина размера является `max-width`, а не безусловной фиксированной шириной.

При недостатке места:

- Drawer сжимается до доступной ширины;
- новые промежуточные размеры не создаются;
- Viewport Drawer не выходит за границы viewport;
- Contained Drawer не выходит за границы Modal;
- на узком экране Drawer может занимать 100% ширины;
- скругление со стороны края экрана может быть уменьшено или убрано;
- внутренние отступы могут адаптироваться отдельными responsive tokens, но не произвольно.

Для Contained Drawer на desktop желательно сохранять видимую часть родительской Modal.

Рекомендуемый минимальный остаток контекста — `64 px`.

Если Container слишком узкий:

1. Drawer сжимается.
2. На узком экране занимает всю ширину Container.
3. Если задача перестаёт читаться — используется Viewport Drawer или другой контейнер.

# 10. Анатомия

```txt
Drawer layer
├─ Scrim
└─ Drawer surface
   ├─ Header
   │  ├─ Back, optional
   │  ├─ Title group
   │  ├─ Context actions, optional
   │  └─ Close
   ├─ Body
   └─ Footer, optional
```

## 10.1. Surface

Базовые параметры:

- фон: системный surface;
- скругление: `24 px` по открытой стороне;
- тень: системная overlay shadow;
- высота: весь доступный контейнер;
- overflow поверхности: hidden;
- Body — единственная основная scroll-зона.

Для Viewport Drawer у правого края правые углы могут быть без скругления.

Для Contained Drawer скругление должно учитывать форму Modal и не выходить за её границы.

## 10.2. Внутренние отступы

Базовый горизонтальный отступ:

```txt
32 px
```

Используется в:

- Header;
- Body;
- Footer.

Не создавать разные отступы для двух продуктов без отдельного системного решения.

## 10.3. Header

Header:

- всегда видим;
- не прокручивается вместе с Body;
- содержит идентификацию текущего уровня;
- не перегружается длинным описанием;
- сохраняет одинаковую геометрию во всех продуктах.

Может содержать:

- кнопку «Назад»;
- заголовок;
- краткое описание;
- ID;
- статус;
- компактный tag;
- контекстные действия;
- кнопку закрытия.

### Заголовок

Заголовок должен:

- описывать текущую задачу или сущность;
- быть понятным без чтения Body;
- не повторять название родительского экрана без необходимости;
- изменяться при замене содержимого на новый внутренний уровень.

### Описание

Краткое описание допустимо, если помогает понять задачу.

Не помещать в Header:

- длинное обоснование;
- сложную аналитику;
- большую форму;
- полный summary;
- список действий;
- контент, который должен прокручиваться.

## 10.4. Кнопки Back и Close

Обе кнопки:

- круглые;
- размер интерактивной области `44 × 44 px`;
- используют системные иконки;
- имеют hover, active и focus состояния;
- имеют доступное текстовое имя.

### Back

Кнопка «Назад»:

- находится слева;
- показывается только при внутренней навигации;
- возвращает на предыдущий уровень того же Drawer;
- не закрывает Drawer;
- не создаёт новый слой.

### Close

Кнопка закрытия:

- всегда находится внутри Header;
- находится справа;
- закрывает только верхний активный Drawer;
- не закрывает весь стек;
- не заменяет Back.

Внешний крестик за границами Drawer не используется.

## 10.5. Body

Body:

- занимает всё оставшееся пространство;
- является основной scroll-зоной;
- имеет отступы `32 px`;
- сохраняет Header и Footer на месте;
- поддерживает длинный контент;
- не заставляет прокручиваться весь viewport или Modal.

Body может содержать:

- форму;
- список;
- карточки;
- историю;
- preview;
- AI-блок;
- summary;
- метаданные;
- источники;
- loading;
- empty;
- error;
- success;
- no access.

## 10.6. Footer

Footer опционален.

Используется, если действия относятся ко всему Drawer:

- применить;
- сохранить;
- продолжить;
- подтвердить;
- принять;
- отклонить;
- отменить;
- удалить.

Footer:

- остаётся фиксированным внизу;
- не исчезает при длинном контенте;
- имеет отступы `16 px 32 px` или системный footer token;
- отделяется border;
- не перекрывает Body;
- учитывает safe area;
- сохраняет действия доступными независимо от прокрутки.

Если действия относятся к отдельной карточке или блоку, они размещаются в этом блоке, а не в общем Footer.

# 11. Варианты Footer

```ts
type DrawerFooterVariant =
  | 'none'
  | 'single'
  | 'standard'
  | 'split'
  | 'stepper';
```

## 11.1. None

Использовать:

- для просмотра;
- для истории;
- для справочной информации;
- если все действия локальные;
- если закрытия достаточно.

## 11.2. Single

Одно основное действие.

```txt
[ Применить ]
```

Подходит:

- для простого фильтра;
- для подтверждения выбора;
- для завершения короткого шага.

В S и M кнопка может занимать всю доступную ширину.

## 11.3. Standard

Secondary + Primary.

```txt
[ Отменить ] [ Сохранить ]
```

Правила:

- действия равнозначно доступны;
- Primary справа;
- в узких Drawer кнопки могут занимать равные колонки;
- не дублировать Close действием «Закрыть», если это не отдельный пользовательский результат.

## 11.4. Split

Независимое или destructive действие слева, завершение справа.

```txt
[ Удалить ]                 [ Отменить ] [ Сохранить ]
```

Использовать, когда destructive action относится ко всему Drawer.

## 11.5. Stepper

Навигация по линейному сценарию.

```txt
[ Назад ]                   [ Продолжить ]
```

Не путать кнопку Footer «Назад» с Header Back:

- Footer «Назад» меняет шаг линейного процесса;
- Header Back возвращает предыдущий экран внутри Drawer;
- Close завершает работу с Drawer.

---

# 12. Блокировка и scrim

Drawer по умолчанию блокирующий.

Пока он открыт:

- нижний слой недоступен мышью;
- нижний слой недоступен с клавиатуры;
- фокус удерживается в верхнем Drawer;
- прокрутка нижнего слоя блокируется;
- нижний слой помечается как inert;
- screen reader не должен воспринимать нижний слой как активный.

## Viewport scrim

Покрывает весь viewport.

## Container scrim

Покрывает весь родительский Container, включая его Header, Body и Footer.

## Несколько слоёв

Визуальное затемнение не должно бесконтрольно суммироваться.

Пользователь должен воспринимать:

- один активный верхний слой;
- сохранённый, но вторичный контекст;
- понятную глубину интерфейса.

---

# 13. Открытие и закрытие

Drawer может закрываться:

- кнопкой Close;
- клавишей Escape;
- действием «Отменить»;
- успешным завершением;
- программно;
- нажатием на scrim, если это разрешено сценарием.

```ts
type DrawerCloseReason =
  | 'close-button'
  | 'escape'
  | 'scrim'
  | 'cancel'
  | 'submit'
  | 'programmatic';
```

## 13.1. Базовые правила

- закрывается только верхний Drawer;
- состояние нижних слоёв сохраняется;
- после закрытия фокус возвращается к trigger;
- Escape работает только для верхнего слоя;
- закрытие родительской Modal при открытом Contained Drawer сначала обрабатывает Drawer;
- открытие и закрытие не должны менять URL, если это не предусмотрено продуктом.

## 13.2. Закрытие по scrim

Допускается для:

- read-only Drawer;
- фильтров без несохранённых данных;
- лёгких сценариев, где потеря состояния невозможна.

Не рекомендуется для:

- длинной формы;
- редактирования;
- загруженных файлов;
- сценария с dirty state;
- критического пользовательского действия.

## 13.3. Несохранённые изменения

Любой способ закрытия должен проходить через единый guard.

```ts
onBeforeClose?: (
  reason: DrawerCloseReason
) => boolean | Promise<boolean>;
```

Guard может:

- разрешить закрытие;
- отменить закрытие;
- показать подтверждение;
- предложить сохранить;
- объяснить последствия.

Нельзя терять данные только потому, что пользователь нажал Escape или scrim.

---

# 14. Вложенность и навигация

Есть три основных паттерна.

## 14.1. Replace content

Использовать, если новый экран — продолжение той же задачи.

Пример:

```txt
История версий
→ Версия 3.4
→ Источник изменения
```

Поведение:

- новый Drawer не создаётся;
- scrim не добавляется;
- ширина не меняется;
- Body заменяется;
- Header обновляется;
- появляется Back;
- состояние предыдущего уровня сохраняется;
- Close закрывает весь Drawer.

Подходит для:

- детализации строки;
- версии;
- источника;
- шага одного сценария;
- локальной настройки;
- последовательного выбора.

## 14.2. Drawer over Drawer

Использовать, если открывается самостоятельная связанная сущность или независимая задача.

Пример:

```txt
Drawer риска
└─ Drawer связанной меры
```

Новый слой оправдан, если:

- верхний объект имеет собственное состояние;
- его можно закрыть независимо;
- пользователь должен вернуться к нижнему Drawer;
- замена содержимого разрушит текущую задачу;
- новый объект смыслово самостоятельный.

## 14.3. Contained Drawer in Modal

Использовать для локальной вспомогательной задачи внутри Modal.

Пример:

```txt
Modal инцидента
└─ Contained Drawer «Связь с риском»
```

Drawer перекрывает всю Modal, но остаётся внутри неё.

## 14.4. Максимальная глубина

Рекомендуемый предел:

```txt
не более двух одновременно открытых Drawer
```

На следующем уровне использовать:

- Replace content;
- возврат назад;
- Modal;
- Page;
- закрытие промежуточного слоя.

Не создавать бесконечный стек боковых поверхностей.

# 15. Паттерны содержимого

Drawer shell остаётся одинаковым. Содержимое формирует композиционные паттерны.

## 15.1. Filter Drawer

Назначение:

- полный набор фильтров;
- точная настройка выборки.

Рекомендуемый размер:

- S или M.

Footer:

- «Сбросить» + «Применить»;
- либо одно «Применить».

Правила:

- быстрые фильтры остаются на странице;
- Drawer содержит расширенный набор;
- активные фильтры после применения отражаются на странице;
- закрытие без применения не должно незаметно менять выдачу, если не используется live filtering.

## 15.2. History Drawer

Назначение:

- версии;
- изменения;
- авторы;
- даты;
- причины;
- источники.

Рекомендуемый размер:

- M;
- L для сложной истории.

Footer:

- обычно отсутствует.

Навигация:

- версия открывается через Replace content;
- самостоятельная сущность может открыться вторым Drawer.

## 15.3. Select entity Drawer

Назначение:

- поиск;
- фильтрация;
- выбор связанного объекта.

Рекомендуемый размер:

- M.

Footer:

- «Отменить» + «Выбрать»;
- «Привязать»;
- кнопка недоступна без выбора.

Правила:

- выбор не должен теряться при прокрутке;
- выбранное состояние явно видно;
- empty state объясняет, как найти объект;
- при одиночном выборе допустимо завершение по клику только для простого и безопасного сценария.

## 15.4. Create or Edit Drawer

Назначение:

- дополнительное создание;
- редактирование;
- настройка.

Рекомендуемый размер:

- S, M или L.

Footer:

- «Отменить» + «Сохранить»;
- «Назад» + «Продолжить» для шагов.

Правила:

- dirty guard обязателен;
- ошибки показываются рядом с полями и в summary при необходимости;
- Primary action не исчезает при прокрутке;
- длинные формы делятся на смысловые секции;
- ширина не увеличивается из-за формы.

## 15.5. Detail or Preview Drawer

Назначение:

- краткая связанная информация;
- доказательство;
- источник;
- объяснение;
- preview сущности.

Рекомендуемый размер:

- S или M;
- L при сложном составе.

Footer:

- обычно отсутствует;
- может содержать переход к полному объекту.

Не использовать как постоянную замену Object Modal.

## 15.6. Review and Approval Drawer

Назначение:

- предложение изменения;
- спор;
- комментарий;
- согласование локального шага.

Рекомендуемый размер:

- M или L.

Footer:

- действия решения должны быть фиксированы;
- destructive/reject и accept визуально различаются;
- причина и последствия решения должны быть понятны до действия.

## 15.7. AI Explanation Drawer

Назначение:

- объяснить вывод;
- показать источники;
- показать доказательства;
- раскрыть логику AI;
- дать связанный следующий шаг.

Рекомендуемый размер:

- M или L.

Правила:

- AI-блок привязан к текущему объекту;
- summary перед деталями;
- источники видимы;
- объяснение структурировано;
- Drawer не превращается в абстрактный чат;
- кнопка перехода к связанному объекту ведёт в правильный слой.

## 15.8. Workspace Drawer XL

Назначение:

- редкая широкая рабочая задача;
- сложная аналитика;
- большая композиция.

Рекомендуемый размер:

- XL.

Правила:

- использовать только системный XL;
- не создавать дополнительные ширины;
- проверить, не нужен ли Page или Modal;
- сохранить ту же анатомию и поведение;
- не использовать XL только потому, что текущая форма плохо скомпонована.

---

# 16. Состояния

Состояния находятся внутри Body и не создают отдельные варианты shell.

Поддерживаются:

- default;
- loading;
- empty;
- error;
- success;
- no access;
- dirty;
- submitting.

## Loading

- Header остаётся доступен;
- Close работает, если закрытие допустимо;
- Footer может быть disabled;
- skeleton повторяет структуру содержимого;
- не менять ширину и высоту Drawer.

## Empty

Empty state должен:

- объяснить, почему нет данных;
- дать следующий шаг;
- не выглядеть как ошибка;
- сохранять контекст задачи.

## Error

Error state должен:

- объяснить, что не удалось;
- содержать retry, если повтор возможен;
- не уничтожать введённые данные;
- не заменять Drawer неожиданным Dialog.

## Submitting

- Primary action показывает loading;
- повторное отправление блокируется;
- закрытие регулируется продуктовым риском;
- пользователь понимает, можно ли продолжать работу.

# 17. Визуальные правила

Базовые параметры:

| Параметр | Значение |
|---|---|
| Content padding | 32 px |
| Header padding | 32 px |
| Footer horizontal padding | 32 px |
| Corner radius | 24 px |
| Back button | 44 × 44 px, circle |
| Close button | 44 × 44 px, circle |
| Scroll area | Body only |
| Header | fixed/sticky |
| Footer | fixed/sticky, optional |
| Surface | system surface |
| Border | system border |
| Shadow | system overlay shadow |
| Scrim | system overlay scrim |

Запрещено:

- внешний Close;
- квадратные Back/Close без системного решения;
- разные радиусы в двух продуктах;
- разные внутренние отступы для одинакового размера;
- Footer, который уезжает под скролл;
- Body, который прокручивает Header;
- Drawer без визуально понятной границы с контекстом;
- произвольные цвета вне токенов UI Kit.

---

# 18. Анимация

Drawer появляется справа налево.

Рекомендуемые параметры:

- открытие: `200–280 ms`;
- закрытие: `160–240 ms`;
- scrim: fade;
- easing: системный overlay easing;
- вложенный Drawer должен визуально восприниматься как новый верхний слой;
- Replace content не должен имитировать создание нового Drawer.

При `prefers-reduced-motion`:

- перемещение сокращается или отключается;
- сохраняется понятная смена состояния;
- фокус переводится без задержки.

---

# 19. Accessibility

Drawer должен:

- иметь роль `dialog`;
- иметь доступное имя;
- использовать `aria-modal="true"` для активного блокирующего слоя;
- связывать заголовок через `aria-labelledby`;
- связывать описание через `aria-describedby`, если оно есть;
- удерживать фокус внутри;
- переводить фокус после открытия;
- возвращать фокус к trigger после закрытия;
- закрываться через Escape, если это не запрещено сценарием;
- иметь видимый focus;
- иметь текстовые названия Back и Close;
- делать нижние слои inert;
- не допускать доступа screen reader к заблокированным слоям;
- сохранять корректный tab order;
- поддерживать reduced motion;
- иметь touch target не меньше `44 × 44 px`.

# 23. Правила для разработчиков

Реализация должна:

- использовать один Drawer shell;
- поддерживать четыре размера;
- поддерживать два scope;
- рендерить Contained Drawer внутри container;
- позволять Contained Drawer перекрывать Header, Body и Footer Modal;
- не позволять Drawer выходить за границы container;
- использовать Portal для Viewport Drawer;
- поддерживать focus trap;
- возвращать фокус;
- блокировать scroll родителя;
- делать нижние слои inert;
- обрабатывать Escape только верхним слоем;
- не закрывать весь стек одним действием;
- централизованно обрабатывать dirty guard;
- использовать UI Kit tokens;
- не принимать произвольный `width` как публичный prop;
- не принимать произвольный `borderRadius` как публичный prop;
- не дублировать Header/Footer в продуктовых компонентах;
- хранить body states отдельно от shell variants.

# 24. Правила для AI-агентов

## 24.1. Обязательный алгоритм выбора

AI-агент перед генерацией интерфейса должен выполнить шаги:

1. Определить основную задачу пользователя.
2. Определить родительский контекст.
3. Проверить, является ли задача самостоятельной.
4. Если самостоятельная — выбрать Page или Modal.
5. Если подчинённая — выбрать Drawer.
6. Определить `scope`.
7. Выбрать один из размеров S, M, L, XL.
8. Определить, нужен ли Footer.
9. Определить close behavior.
10. Проверить dirty state.
11. Определить Replace или Stack.
12. Проверить глубину вложенности.
13. Проверить responsive.
14. Проверить accessibility.
15. Только после этого генерировать UI или код.

## 24.2. Decision table для AI

| Условие | Решение |
|---|---|
| Основной объект и решение | Modal |
| Самостоятельная длительная работа | Page |
| Подчинённая задача с сохранением контекста | Drawer |
| Локальная задача внутри Modal | Contained Drawer |
| Самостоятельная сущность поверх Modal | Viewport Drawer |
| Следующий уровень той же задачи | Replace content |
| Независимый связанный объект | Drawer over Drawer |
| Третий физический Drawer | Не создавать |
| Только просмотр | Footer none |
| Общая форма | Footer standard |
| Один шаг | Footer single |
| Destructive + save | Footer split |
| Линейный процесс | Footer stepper |

## 24.3. Выбор размера AI-агентом

```txt
S:
- фильтр;
- комментарий;
- короткая форма;
- простая настройка.

M:
- стандартный случай;
- история;
- редактирование;
- выбор сущности;
- детали.

L:
- сложная форма;
- две колонки;
- много секций;
- review.

XL:
- редкая широкая работа;
- аналитика;
- сложная композиция.
```

Если AI не может обосновать L или XL, использовать M.

## 24.4. AI запрещено

- придумывать новую ширину;
- использовать `width: 650px`, `742px`, `850px` и другие legacy значения;
- создавать отдельный Drawer для каждого продукта;
- выносить Close за границы Drawer;
- размещать Back справа;
- делать Header или Footer частью scroll Body;
- открывать новый Drawer для каждого шага;
- создавать третий Drawer;
- использовать Drawer вместо основного Object Modal;
- закрывать весь стек при закрытии верхнего слоя;
- терять состояние родителя;
- включать закрытие по scrim для dirty form без guard;
- использовать Footer без общего действия;
- использовать цвета, отступы и радиусы вне UI Kit tokens;
- создавать Side panel и называть его Drawer;
- генерировать постоянный Drawer без scrim как стандартный паттерн;
- менять ширину при внутренней навигации;
- делать Contained Drawer только внутри Body Modal: он должен перекрывать всю Modal;
- оставлять доступным Header или Footer Modal под Contained Drawer.

## 24.5. Формат описания Drawer для AI handoff

AI должен выдавать конфигурацию:

```yaml
component: Drawer
```


# 26. Антипаттерны

## Произвольная ширина

Плохо:

```txt
Drawer width = 742 px
```

Хорошо:

```txt
Drawer size = M / 720 px
```

## Новый слой для каждого шага

Плохо:

```txt
Drawer
→ Drawer
→ Drawer
→ Drawer
```

Хорошо:

```txt
Drawer
→ Replace content
→ Replace content
```

## Contained Drawer только поверх Body

Плохо:

```txt
Modal Header остаётся активным
Modal Body перекрыт Drawer
Modal Footer остаётся активным
```

Хорошо:

```txt
Contained Drawer перекрывает всю Modal:
Header + Body + Footer
```

## Drawer как Object Modal

Плохо:

- основной риск всегда открывается в Drawer;
- пользователь принимает главное решение в случайной боковой панели.

Хорошо:

- основной объект открывается в Modal;
- Drawer раскрывает связанную или дополнительную задачу.

## Footer внутри скролла

Плохо:

- пользователь должен прокрутить длинную форму до конца, чтобы сохранить.

Хорошо:

- Footer фиксирован;
- Body прокручивается отдельно.

# 27. DoD для дизайна

Drawer готов, если:

- [ ] выбран правильный контейнер;
- [ ] задача действительно подчинённая;
- [ ] используется один из четырёх размеров;
- [ ] нет произвольной ширины;
- [ ] выбран Viewport или Container;
- [ ] Contained Drawer перекрывает всю Modal;
- [ ] отступы контента 32 px;
- [ ] радиус 24 px;
- [ ] Back и Close круглые 44 × 44 px;
- [ ] Close находится внутри Header;
- [ ] Header не прокручивается;
- [ ] Footer не прокручивается;
- [ ] Body является единственной scroll-зоной;
- [ ] Footer соответствует типу задачи;
- [ ] dirty state обработан;
- [ ] Back и Close имеют разный смысл;
- [ ] вложенность не превышает два Drawer;
- [ ] responsive проверен на 1366 px и уже;
- [ ] loading, empty и error не ломают shell;
- [ ] после закрытия понятен возврат пользователя;
- [ ] оба продукта используют одинаковый shell.

# 28. DoD для разработки

Реализация готова, если:

- [ ] размеры S/M/L/XL реализованы токенами;
- [ ] произвольный width отсутствует в публичном API;
- [ ] Viewport Drawer рендерится в overlay root;
- [ ] Contained Drawer рендерится в container;
- [ ] Container Drawer перекрывает Header/Body/Footer Modal;
- [ ] focus trap работает;
- [ ] Escape закрывает только верхний слой;
- [ ] focus возвращается к trigger;
- [ ] parent scroll заблокирован;
- [ ] нижний слой inert;
- [ ] close reason передаётся в callback;
- [ ] dirty guard единый для всех способов закрытия;
- [ ] Header и Footer fixed/sticky;
- [ ] Body scroll независимый;
- [ ] Back не закрывает Drawer;
- [ ] stack manager ограничивает глубину;
- [ ] reduced motion поддержан;
- [ ] keyboard navigation проверена;
- [ ] UI Kit tokens используются;
- [ ] тесты покрывают close, escape, focus return, dirty guard и stack.
