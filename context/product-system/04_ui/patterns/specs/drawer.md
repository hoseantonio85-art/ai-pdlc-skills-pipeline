# Drawer: общий дизайн-контракт NORM и ORM

**Статус:** актуальная редакция дизайн-правил для продолжения работы, но **не** подтверждённый API production UI Kit. Для быстрого чтения используйте [runtime контракт](../runtime/drawer.md). 

## Когда использовать

Drawer — блокирующая вторичная поверхность для задачи, выполняемой без потери исходного контекста Page, Modal или предыдущего Drawer. Основной самостоятельный объект или длительная рабочая задача — Object Modal/Page. Side panel — постоянная боковая область, не Drawer.

## Четыре независимые оси

- **Theme** — NORM/ORM: визуальный продуктовый контекст.
- **Scope** — `viewport` или `container`: границы перекрытия.
- **Size** — S/M/L/XL: системная ширина.
- **Navigation** — каскад, смена режима текущего Drawer, переключение соседних объектов, возможный локальный переход.

Тема **не меняется** от того, открыт Drawer внутри Modal или поверх viewport.

| Аспект | NORM | ORM |
|---|---|---|
| Surface | Отдельная, скруглённая со всех сторон | Правый слой, привязанный к краю scope |
| Close | Внутри Header в показанных вариантах | **Внешняя кнопка** входит в композицию Drawer |
| Размер нового каскадного слоя | Такой же или на **один пресет меньше** | Все новые слои одного размера |
| Переключение соседних объектов | Возможно, но не утверждено как стандарт темы | Опционально по упорядоченной коллекции |

## Scope и overlay

`viewport` привязывает Drawer к правому краю окна; в ORM его можно открывать поверх уже открытой Modal (нижняя Modal сохраняет состояние).

`container` привязывает Drawer к краю родительской Modal **в её границах**. Drawer перекрывает **Header, Body и Footer** родителя целиком, собственный overlay покрывает всю Modal.

**Каждый новый Drawer получает собственный overlay**. Активен только верхний; нижние сохраняют состояние и не получают ввод. Точная визуальная композиция нескольких overlay и opacity-токены требуют сверки с UI Kit.

## Размеры

| Пресет | Ширина | Обычно |
|---|---:|---|
| S | 608 px | Фильтр, комментарий, небольшие настройки |
| M | 720 px | Стандартная форма, история, связь |
| L | 840 px | Сложная форма и несколько секций |
| XL | 1184 px | Редкая аналитическая/широкая композиция |

Произвольную ширину под один экран не добавлять. **Правило размера каскада касается только следующего нового Drawer**, а не изменения режима View/Edit того же Drawer.

На узком viewport и внутри слишком узкой Modal точное responsive-поведение **ещё не утверждено**. Не выдавать старые гипотезы `max-width`, mobile 100% или конкретные остатки фона за норматив. Не допускать физического обрезания интерактивных действий.

## Анатомия

```text
Drawer layer + overlay
└─ Drawer surface
   ├─ Header — заголовок, контекст, статус, Close по теме, Back только по решению сценария
   ├─ Body — единственная основная зона прокрутки
   └─ Footer? — фиксированные общие действия; иначе отсутствует
```

Header и Footer не прокручиваются с Body. Локальные действия карточки — у карточки, общие «Сохранить», «Применить», «Отменить» — при необходимости в Footer. Индикатор статуса и подсветка Header нужны при реальном бизнес-смысле, точные уровни и цвета пока не утверждены.

**Старые ориентиры 32 px отступов, 24 px радиуса, 44×44 px контролов** не считать подтверждёнными одинаковыми UI Kit tokens обеих тем.

## Закрытие и возврат

Close всегда закрывает **только активный верхний Drawer**. Нижний Drawer или Modal остаются в прежнем состоянии. В ORM внешние Close при каскаде позволяют закрывать слои последовательно.

**Escape по умолчанию выключен**. Его можно явно включить для конкретного сценария; тогда он действует на верхний слой.

**Не определено:** закрытие по клику на overlay; универсальное поведение при несохранённых изменениях (Close, Escape, переключение объекта, закрытие родителя). Нельзя обещать автосохранение, бесшумную потерю данных или всегда одинаковый confirmation-flow.

## Каскад и соседние объекты

**Жёсткого ограничения глубины двумя Drawer нет.** Для NORM обычно до трёх; четвёртый допустим с обоснованием, пятый — редкий и требует UX-проверки. В ORM больше двух допустимо, после третьего нужна особая осторожность. Это рекомендации, не технический максимум.

Не открывать новый слой автоматически для каждого шага формы. Если нужно отредактировать текущий объект, можно перейти в Edit того же Drawer.

**Back / replace content** присутствуют в референсах, но пока **не утверждены** универсально. Не создавать Back автоматически. Для самостоятельной связанной сущности рассмотреть новый Drawer.

**Вертикальное переключение соседних объектов** — переход между объектами определённого упорядоченного списка внутри одного Drawer. Это не Back и не новый слой. В ORM опционально; в NORM пока не является правилом темы.

## Типичные сценарии

- Фильтр: часто S/M и общий Footer «Сбросить/Применить» (draft/applied состояние определяет сценарий).
- История/источник: часто без Footer.
- Просмотр и редактирование: смена режима возможна в текущем Drawer, общие действия в Footer.
- Выбор связанного объекта: вернуть пользователя к прежнему контексту после завершения.
- Вложение в Modal: `container`, если задача остаётся внутри родителя; `viewport` — если нужно перекрыть окно.

## Неутверждённые вопросы

- Универсальная dirty-state close policy и клик по overlay.
- Точные адаптивные сценарии для узкого viewport/Modal.
- Цвета/уровни status-индикатора и header highlight.
- Обязательность Back/replace и история локальной навигации.
- Motion, focus, aria/accessibility глубоко вложенного каскада.
- Совмещение нескольких overlay и точные UI Kit tokens.

**Для инженерной реализации:** проверить реальный UI Kit и frontend целевого проекта; этот текст — дизайн-контракт, не описание подтверждённых exports.
