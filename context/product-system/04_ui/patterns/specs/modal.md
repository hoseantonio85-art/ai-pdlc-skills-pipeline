# Modal — паттерн и компонент

## 1. Назначение документа

Документ описывает единые правила проектирования, выбора и реализации модальных окон в продуктовой системе **UI Kit AI PDLC Ready**.

Он нужен прежде всего AI-агентам, которые собирают прототипы и интерфейсы, а также дизайнерам, аналитикам, product owners и разработчикам.

Документ является общим контрактом для двух продуктов:

- **ORM** — внутренняя система управления операционными рисками;
- **NORM** — коммерческий продукт управления операционными рисками.

В продуктах используются разные геометрические профили больших объектных модалок, но их сценарные и композиционные паттерны должны быть общими.

---

# 2. Определение

**Modal** — блокирующая поверхность поверх текущего интерфейса, которая переводит пользователя в отдельный фокус: просмотр самостоятельного объекта, создание, редактирование, принятие решения, выполнение формы или получение важной информации.

Modal сохраняет родительский контекст, но временно делает его недоступным.

После закрытия пользователь возвращается:

- к исходной странице или предыдущей модалке;
- с сохранённым состоянием нижнего слоя;
- с сохранённой прокруткой и выбором;
- к элементу, из которого модалка была открыта.

## Ключевая формула

> Page = самостоятельная постоянная рабочая область.  
> Modal = основной фокус, самостоятельный объект или важное решение.  
> Drawer = подчинённая задача без потери контекста.  
> Dialog / Confirm = короткий композиционный паттерн внутри Modal shell.

Modal определяется ролью задачи, а не только шириной.

---

# 3. Когда использовать Modal

Использовать Modal, когда:

- открывается самостоятельный объект для полноценного просмотра;
- пользователь создаёт или редактирует объект, не покидая родительский раздел;
- нужно принять важное решение;
- требуется короткая или средняя форма;
- нужно показать информационный или процессный экран;
- пользователь загружает документы;
- требуется выбор одного из нескольких сценариев;
- нужно подтвердить действие или предупредить о последствиях;
- открывается связанный самостоятельный объект поверх уже открытого объекта;
- родительский контекст важно сохранить, но взаимодействие с ним во время работы недопустимо.

---

# 4. Когда не использовать Modal

Не использовать Modal, если:

- задача является постоянным самостоятельным разделом продукта;
- пользователю нужен отдельный URL, закладка или длительная навигация;
- требуется одновременная работа с родительской страницей;
- задача подчинённая и должна выполняться без потери текущего объекта — использовать Drawer;
- действие помещается в локальное меню, Popover или простой inline-control;
- модалка используется как постоянная боковая панель;
- большая объектная форма фактически стала отдельным многоэкранным продуктом;
- для каждого шага одной формы создаётся новая модалка вместо внутренних шагов;
- окно открывается только ради короткой подсказки, которую можно показать inline.

---

# 5. Семейство Modal

В системе используется один базовый Modal shell и несколько композиционных паттернов.

```txt
Modal
├─ Small / compact patterns
│  ├─ Confirm
│  ├─ Comment or reason form
│  ├─ Compact information
│  └─ Small choice
├─ Standard patterns
│  ├─ Form
│  ├─ File upload
│  ├─ Information
│  ├─ Process / progress
│  └─ Scenario selection
└─ Object Modal
   ├─ Object View
   ├─ Object Create
   ├─ Object Edit
   └─ Stacked Object Modal
```

Размер, назначение и режим являются независимыми свойствами.

# 6. Системные размеры

В системе используются пять базовых ширин.

```ts
type ModalSize =
  | 'S'
  | 'M'
  | 'L'
  | 'object';
```

Размер `object` получает фактическую ширину из продуктового профиля.

| Размер | Ширина | Основные сценарии | Продукты |
|---|---:|---|---|
| S | 550 px | Короткое подтверждение, предупреждение, простое решение | NORM; допустим в ORM при необходимости |
| M | 650 px | Небольшая форма, комментарий, причина, чекбоксы, локальная информация | ORM и NORM |
| L | 800 px | Стандартная форма, загрузка файлов, информационный экран, процесс, выбор сценария | ORM и NORM |
| Object / NORM | 1320 px | Просмотр, создание и редактирование самостоятельных объектов | NORM |
| Object / ORM | 1424 px | Просмотр, создание и редактирование самостоятельных объектов в near-fullscreen workspace | ORM |

## 6.1. Правила выбора размера

Выбирать размер по структуре задачи, а не по длине случайного текста.

### S — 550 px

Использовать для:

- короткого подтверждения;
- предупреждения о потере прогресса;
- простого выбора «продолжить / отменить»;
- короткой информации с одним решением.

Не использовать, если появляется длинная форма, список или несколько смысловых блоков.

### M — 650 px

Использовать для:

- небольшой формы;
- ввода комментария или причины;
- согласования или отклонения;
- выбора нескольких пунктов;
- просмотра одного компактного информационного блока;
- короткого списка комментариев.

### L — 800 px

Использовать для:

- загрузки документов;
- средней формы;
- выбора сценария;
- информационной композиции с иллюстрацией;
- процессного состояния;
- onboarding-экрана;
- формы с несколькими секциями;
- длинного контента с фиксированным Footer.

### Object — 1320 / 1424 px

Использовать для:

- полноценного просмотра самостоятельного объекта;
- создания объекта;
- редактирования объекта;
- сложного объекта с секциями, навигацией, правой колонкой и связанными действиями;
- открытия связанного самостоятельного объекта поверх другого объекта.

## 6.2. Запрещено

- произвольная ширина под конкретный макет;
- создание новых промежуточных размеров без системного решения;
- выбор Object Modal только потому, что форма плохо скомпонована;
- изменение ширины при переходе между режимами одного объекта;
- использование ширины 1320 в ORM или 1424 в NORM без осознанного продуктового решения;
- передача произвольного `width` как публичного prop.

# 7. Продуктовые профили Object Modal

Object Modal является общим паттерном с двумя геометрическими профилями.

```ts
type ModalProductProfile = 'orm' | 'norm';
```

## 7.1. NORM Object Modal

```txt
Width: 1320 px
Perception: большая объектная модалка поверх продукта
```

Особенности:

- вокруг поверхности заметен родительский интерфейс;
- модалка сохраняет выраженное ощущение overlay;
- используется для просмотра, создания и редактирования объектов;
- поддерживает стек связанных Object Modal;
- при наличии стека под активной модалкой показывается одна декоративная подложка слева;
- выбранный раздел, скролл и состояние каждого слоя сохраняются.

## 7.2. ORM Object Modal

```txt
Width: 1424 px
Perception: near-fullscreen объектный workspace
```

Особенности:

- поверхность занимает почти весь viewport;
- родительский контекст виден минимально;
- используется для просмотра, создания и редактирования объектов;
- может содержать широкую рабочую композицию или узкую центрированную форму;
- воспринимается как временное рабочее пространство, но остаётся Modal и сохраняет родительскую страницу.

## 7.3. Что должно быть общим

Несмотря на различие ширины, в обоих продуктах должны совпадать:

- базовый Modal shell;
- роли Header, Body, Right rail и Footer;
- правила просмотра объекта;
- правила создания и редактирования;
- блокировка нижних слоёв;
- управление фокусом;
- скролл;
- dirty guard;
- открытие подчинённых Drawer;
- семантика Close;
- восстановление состояния после закрытия верхнего слоя.

# 8. Анатомия Modal

```txt
Modal layer
├─ Scrim
└─ Modal surface
   ├─ Topbar / Header
   │  ├─ Navigation, optional
   │  ├─ Identity / title group
   │  ├─ Context controls, optional
   │  └─ Close
   ├─ Object Header, optional
   │  ├─ Type / ID / status
   │  ├─ Title
   │  ├─ Description
   │  └─ Section navigation, optional
   ├─ Body
   │  ├─ Main content
   │  └─ Right rail, optional
   └─ Footer, optional
```

Не каждый размер обязан использовать все зоны.

### Small и Standard Modal

Обычно используют:

```txt
Header
Body
Footer, optional
```

### Object Modal

Обычно используют:

```txt
Topbar
Object Header
Body: Main + Right rail
Footer только для create/edit
```

# 9. Header и Topbar

Header:

- всегда содержит понятное название текущей задачи или объекта;
- содержит Close;
- не прокручивается вместе с Body;
- не перегружается длинной аналитикой и формами;
- может содержать Back, служебный контекст и компактные действия;
- сохраняет одинаковую смысловую структуру в ORM и NORM.

## 9.1. Что допустимо в Header

- Back;
- ID объекта;
- тип объекта;
- статус;
- название сценария;
- краткое описание;
- системный контекст;
- переход в связанный режим;
- Close.

## 9.2. Что не помещать в Header

- длинные формы;
- большие AI-summary;
- полноценную аналитику;
- список объектных действий просмотра;
- destructive actions просмотра;
- действия создания и сохранения всей формы;
- контент, который должен прокручиваться.

---

# 10. Close и Back

## 10.1. Close

Close:

- всегда находится внутри Header;
- закрывает только текущую активную модалку;
- если под ней есть предыдущая модалка, она становится активной;
- если текущая модалка корневая, пользователь возвращается на страницу;
- проходит через dirty guard;
- возвращает фокус к trigger текущего слоя.

## 10.2. Back

Back:

- опционален;
- показывается, когда текущая модалка открыта из другой модалки как связанный объект или внутренний навигационный уровень;
- возвращает пользователя к предыдущему модальному контексту;
- сохраняет состояние предыдущего слоя;
- не закрывает весь стек.

Back и Close могут приводить к закрытию текущего слоя, но выражают разное намерение:

- Back — навигационное возвращение;
- Close — закрытие текущей поверхности.

AI-агент не должен добавлять Back на корневую модалку без истории перехода.

---

# 11. Body и скролл

Body:

- является основной scroll-зоной;
- занимает всё оставшееся пространство;
- не прокручивает Header и Footer;
- сохраняет состояние при открытии верхнего слоя;
- восстанавливает позицию скролла после возврата;
- не заставляет прокручиваться родительскую страницу.

Для Object Modal:

- Main content и Right rail являются частью одной рабочей области;
- Right rail должен оставаться доступным при работе с объектом;
- при длинном содержимом допустим sticky rail или согласованная локальная прокрутка;
- не создавать неконтролируемые вложенные scroll-зоны.

---

# 12. Footer

Footer используется только для действий, относящихся ко всей модалке или форме.

Footer:

- фиксирован внизу;
- не уезжает под скролл;
- отделён от Body;
- не перекрывает контент;
- сохраняет основные действия доступными;
- может отсутствовать.

## 12.1. Footer в просмотре объекта

В `Object View` Footer не используется.

Все объектные действия просмотра находятся в Right rail.

Это правило действует без исключений для ORM и NORM.

## 12.2. Footer в создании и редактировании

В `Object Create` и `Object Edit` основные действия находятся в фиксированном Footer.

Примеры:

```txt
[ Отмена ] [ Сохранить ]
[ Назад ] [ Продолжить ]
[ Отмена ] [ Создать ]
```

Right rail при редактировании может содержать подсказки, статус и метаданные, но не заменяет Footer как место завершения формы.

---

# 13. Паттерн Object View

Object View используется для полноценного изучения самостоятельного объекта.

```txt
Object Modal / View
├─ Topbar
├─ Object Header
├─ Body
│  ├─ Main content
│  └─ Right rail
└─ Footer отсутствует
```

## 13.1. Main content

Main content содержит:

- summary объекта;
- ключевые показатели;
- вкладки или крупные разделы;
- аккордеоны;
- списки связанных данных;
- AI-выводы;
- источники;
- карточки и визуализации.

## 13.2. Right rail

Right rail является единой зоной информации и объектных действий.

Рекомендуемый порядок:

1. Основная информация и метаданные.
2. Статус, владелец, автор, даты.
3. История и коммуникация.
4. Связанные сущности и служебные переходы.
5. Основное объектное действие.
6. Вторичные действия.
7. Destructive или lifecycle actions.

В Right rail размещаются, например:

- редактировать;
- согласовать;
- отклонить;
- добавить меру;
- открыть историю;
- открыть комментарии;
- поделиться;
- исключить из оценки;
- отправить в архив;
- удалить;
- другие действия над объектом.

## 13.3. Запрещено в Object View

- размещать часть действий справа, а часть внизу;
- использовать общий Footer;
- дублировать одно действие в Header и Right rail;
- смешивать объектные действия с локальными действиями карточек;
- делать Main content единственным местом для редких destructive actions.

---

# 14. Паттерн Object Create / Edit

Object Create и Object Edit используют общую рабочую структуру.

```txt
Object Modal / Create or Edit
├─ Topbar
├─ Object Header, optional
├─ Scrollable Body
│  └─ Form workspace
└─ Fixed Footer
```

Правила:

- форма может быть одноколоночной или многоколоночной;
- в ORM допустима узкая центрированная колонка внутри широкого workspace;
- в NORM форма может использовать больше доступной ширины;
- форма делится на смысловые секции;
- аккордеоны используются для разделов, а не для сокрытия обязательной логики;
- ошибки показываются рядом с полями и при необходимости в summary;
- основные действия всегда находятся в Footer;
- dirty guard обязателен;
- закрытие не должно приводить к незаметной потере данных.

---

# 15. Стек Object Modal

Object Modal может открываться поверх другой Object Modal.

Стек не ограничивается фиксированным количеством уровней.

Пример:

```txt
Page
└─ Risk Modal
   └─ Measure Modal
      └─ Incident Modal
         └─ Counterparty Modal
```

## 15.1. Поведение стека

Каждый слой сохраняет:

- выбранный раздел;
- раскрытые секции;
- прокрутку;
- введённые данные;
- фильтры;
- локальное состояние;
- trigger, из которого был открыт следующий слой.

Только верхняя модалка активна.

Нижние слои:

- недоступны мышью;
- недоступны с клавиатуры;
- помечены как inert;
- сохраняются в DOM или state manager;
- не получают Escape;
- не прокручиваются.

## 15.2. Визуальная подложка

Если глубина стека больше одного уровня, под активной модалкой показывается **одна декоративная подложка слева**.

Подложка:

- показывает, что текущая модалка открыта поверх предыдущего объекта;
- не повторяет весь реальный стек;
- не увеличивается с каждым новым уровнем;
- не является интерактивной;
- не содержит отдельного контента;
- не создаёт дополнительный scrim;
- имеет системный небольшой сдвиг и тень;
- исчезает на корневом уровне.

Независимо от глубины стека визуально показывается только одна подложка.

## 15.3. Закрытие слоя

- Close закрывает текущую модалку;
- Back возвращает к предыдущей модалке;
- Escape обрабатывается только верхним слоем и закрывает текущую модалку, если это разрешено;
- после закрытия предыдущая модалка восстанавливается в исходном состоянии;
- scrim не должен становиться темнее при каждом новом уровне.

---

# 16. Модалка или Drawer внутри Object Modal

Использовать новую Object Modal, если открывается самостоятельный связанный объект.

Примеры:

- риск → мера;
- риск → инцидент;
- контрагент → договор;
- объект → другой самостоятельный объект.

Использовать Drawer, если открывается подчинённая задача.

Примеры:

- история;
- комментарий;
- выбор связи;
- настройка;
- уточнение оценки;
- просмотр источника;
- служебные детали;
- локальное добавление данных.

Правило:

```txt
Связанный самостоятельный объект → Object Modal stack.
Подчинённая задача → Drawer.
Следующий шаг одной формы → внутренний step / replace content.
```

# 17. Паттерны Small и Standard Modal

## 17.1. Confirm Modal

Назначение:

- подтвердить или отменить действие;
- предупредить о последствиях;
- подтвердить потерю прогресса;
- подтвердить переход во внешний сервис.

Размер:

- S;
- M, если требуется больше объяснения.

Структура:

```txt
Header
Body: короткое сообщение
Footer: secondary + primary
```

Правила:

- одна основная мысль;
- последствия понятны до действия;
- текст не превращается в длинную инструкцию;
- destructive intent отражается визуально;
- не использовать иллюстрацию, если она не помогает принять решение.

## 17.2. Comment or Reason Modal

Назначение:

- согласовать;
- отклонить;
- указать причину;
- оставить комментарий;
- выбрать несколько элементов и объяснить решение.

Размер:

- M;
- L, если список или форма сложнее.

Структура:

```txt
Header
Body: описание + поля
Footer: отмена + действие
```

Правила:

- intent может быть success, warning или danger;
- поле причины должно иметь понятное назначение;
- обязательность комментария задаётся бизнес-правилом;
- ошибки не должны уничтожать введённый текст.

## 17.3. Compact Information Modal

Назначение:

- показать комментарий;
- показать короткую справку;
- сообщить результат;
- дать одно понятное действие.

Размер:

- S или M.

Footer:

- одно действие;
- либо отсутствует, если Close достаточно.

## 17.4. Scenario Selection Modal

Назначение:

- выбрать один из нескольких сценариев;
- выбрать цель обучения или использования данных;
- определить дальнейший путь.

Размер:

- L.

Правила:

- варианты сравнимы;
- карточки имеют одинаковую структуру;
- выбранное состояние очевидно;
- следующий шаг понятен;
- не открывать отдельную модалку для каждого пояснения варианта.

## 17.5. File Upload Modal

Назначение:

- загрузить документы;
- показать список файлов;
- выбрать область знаний;
- запустить автоматическое заполнение или анализ.

Размер:

- L;
- Object только если загрузка является частью большой объектной формы.

Правила:

- dropzone остаётся заметной;
- список файлов не ломает Footer;
- ошибки файла показываются рядом с файлом;
- загрузка, удаление и повторная попытка не сбрасывают остальные файлы;
- при длинном списке прокручивается Body;
- Primary action фиксирован в Footer.

## 17.6. Information Modal

Назначение:

- объяснить, что произойдёт;
- подготовить пользователя к следующему шагу;
- показать рекомендации;
- описать, какие документы нужны.

Размер:

- L.

Правила:

- summary перед деталями;
- иллюстрация поддерживает смысл, а не заменяет его;
- длинный контент прокручивается;
- действие соответствует следующему шагу;
- не превращать информационную модалку в документацию на несколько экранов.

## 17.7. Process / Progress Modal

Назначение:

- показать, что анализ или обработка начались;
- объяснить ожидаемое время;
- сообщить, может ли пользователь продолжить работу;
- дать безопасное завершение.

Размер:

- L.

Правила:

- состояние процесса сформулировано явно;
- указано, нужно ли ждать;
- указан способ получения результата;
- модалка не имитирует точный прогресс без данных;
- закрытие не отменяет фоновый процесс, если это не сказано явно.

---

# 18. Высота

Ширина системна, высота зависит от паттерна.

## 18.1. Content height

Использовать для:

- подтверждений;
- небольших форм;
- комментариев;
- выбора из нескольких карточек;
- короткой информации.

Поверхность растёт по содержимому до системного `max-height`.

## 18.2. Workspace height

Использовать для:

- загрузки файлов;
- длинных информационных экранов;
- process modal;
- Object Modal;
- больших форм.

Правила:

- Header и Footer остаются на месте;
- Body прокручивается;
- поверхность не выходит за viewport;
- на малой высоте внутренние отступы могут адаптироваться системно.

---

# 19. Состояния

Состояния находятся внутри Body и не создают новый Modal shell.

Поддерживаются:

- default;
- loading;
- empty;
- error;
- success;
- no access;
- dirty;
- submitting;
- background process;

## Loading

- Header остаётся доступен;
- геометрия не меняется;
- Footer может быть disabled;
- skeleton повторяет структуру будущего контента.

## Error

- введённые данные сохраняются;
- ошибка объясняет, что произошло;
- retry находится рядом с проблемой;
- модалка не заменяется неожиданным Confirm.

## Submitting

- повторное отправление блокируется;
- Primary action показывает состояние;
- пользователь понимает, можно ли закрыть окно;
- результат не должен создаваться повторно.

---

# 20. Scrim и блокировка

Modal является блокирующей поверхностью.

Пока Modal открыт:

- нижний слой недоступен мышью;
- нижний слой недоступен с клавиатуры;
- фокус удерживается в активной модалке;
- прокрутка нижнего слоя блокируется;
- нижний слой становится inert;
- screen reader не воспринимает нижний слой как активный.

При стеке:

- визуально используется единый scrim;
- затемнение не суммируется бесконтрольно;
- только верхняя модалка имеет активную modal-семантику.

---

# 21. Открытие и закрытие

Modal может закрываться:

- Close;
- Escape;
- действием «Отмена»;
- успешным завершением;
- программно;
- нажатием на scrim, если это разрешено сценарием.

```ts
type ModalCloseReason =
  | 'close-button'
  | 'back'
  | 'escape'
  | 'scrim'
  | 'cancel'
  | 'submit'
  | 'programmatic';
```

Базовые правила:

- закрывается только текущая активная модалка;
- состояние нижних слоёв сохраняется;
- после закрытия фокус возвращается к trigger текущего слоя;
- Escape обрабатывает только верхний слой;
- scrim не закрывает форму с dirty state без guard;
- закрытие корневой модалки возвращает на Page.

---

# 22. Несохранённые изменения

Все способы закрытия должны проходить через единый guard.

```ts
onBeforeClose?: (
  reason: ModalCloseReason
) => boolean | Promise<boolean>;
```

Guard может:

- разрешить закрытие;
- отменить закрытие;
- показать Confirm;
- предложить сохранить;
- объяснить последствия.

Нельзя терять данные из-за Close, Back, Escape или scrim.

---

# 23. Адаптивность

Ширина Modal является `max-width`, а не безусловной фиксированной шириной.

При недостатке места:

- Modal сжимается до доступной ширины;
- новые промежуточные размеры не создаются;
- сохраняются системные поля от viewport;
- на узком экране Modal может занимать почти всю ширину;
- внутренние колонки перестраиваются;
- Right rail переносится под Main content или становится отдельным внутренним уровнем;
- Footer остаётся доступным;
- Object Modal не выходит за viewport;
- NORM и ORM сохраняют свой продуктовый профиль, пока это позволяет экран.

Для очень узкого viewport нужно проверить, не должен ли сценарий перейти в Page.

---

# 24. Accessibility

Modal должен:

- иметь роль `dialog`;
- иметь доступное имя;
- использовать `aria-modal="true"` для активного слоя;
- связывать заголовок через `aria-labelledby`;
- связывать описание через `aria-describedby`, если оно есть;
- удерживать фокус внутри;
- переводить фокус после открытия;
- возвращать фокус к trigger после закрытия;
- закрываться через Escape, если это разрешено;
- иметь видимый focus;
- давать доступные названия Back и Close;
- делать нижние слои inert;
- не допускать доступа screen reader к заблокированным слоям;
- сохранять корректный tab order;
- поддерживать reduced motion.

В стеке только верхняя модалка активна для assistive technologies.

---

# 25. Анимация

Базовая Modal:

- появляется через fade + небольшое перемещение или scale;
- scrim появляется через fade;
- закрывается быстрее, чем открывается;
- не меняет геометрию после появления.

Stacked Object Modal:

- активная поверхность появляется над предыдущей;
- одна декоративная подложка слева проявляется вместе с верхним слоем;
- подложка не анимируется как самостоятельная модалка;
- scrim не мигает и не становится темнее на каждом уровне.

При `prefers-reduced-motion` перемещение сокращается или отключается.

# 28. Правила для AI-агентов

## 28.1. Обязательный алгоритм выбора

Перед генерацией Modal AI-агент должен:

1. Определить, является ли задача самостоятельной.
2. Проверить, нужен ли Modal, Page, Drawer, Dialog или Popover.
3. Определить продукт: ORM или NORM.
4. Определить режим: view, create, edit, confirm, form, info, process, choice или upload.
5. Выбрать системный размер.
6. Проверить, нужен ли Object Modal.
7. Для Object View создать Main content + Right rail.
8. Перенести все объектные действия просмотра в Right rail.
9. Не создавать Footer в Object View.
10. Для create/edit создать фиксированный Footer.
11. Определить, нужен ли Back.
12. Если открывается связанный объект, использовать Modal stack.
13. Если открывается подчинённая задача, использовать Drawer.
14. При stack depth > 1 показать одну декоративную подложку слева.
15. Проверить dirty state.
16. Проверить scroll и responsive.
17. Проверить accessibility.
18. Только после этого генерировать UI или код.

## 28.2. Decision table

| Условие | Решение |
|---|---|
| Полноценный просмотр самостоятельного объекта | Object Modal / View |
| Создание самостоятельного объекта | Object Modal / Create |
| Редактирование самостоятельного объекта | Object Modal / Edit |
| ORM object | Object width 1424 |
| NORM object | Object width 1320 |
| Короткое подтверждение | S |
| Причина, комментарий, чекбоксы | M |
| Загрузка, процесс, информация, выбор сценария | L |
| Просмотр объекта | Все действия справа |
| Создание или редактирование | Действия в Footer |
| Связанный самостоятельный объект | New Object Modal in stack |
| Подчинённая задача | Drawer |
| Глубина стека больше одного | Одна подложка слева |
| Close | Закрывает текущую модалку |
| Dirty state | Guard before close |

## 28.3. AI запрещено

- придумывать новую ширину;
- смешивать действия просмотра между Header, Right rail и Footer;
- создавать Footer в Object View;
- размещать сохранение большой формы в Right rail;
- использовать 1320 для ORM или 1424 для NORM без системного решения;
- создавать отдельный Modal shell под каждый продукт;
- рисовать несколько декоративных подложек по числу уровней;
- суммировать scrim при глубоком стеке;
- закрывать весь стек одним Close;
- терять состояние предыдущей модалки;
- открывать новый Object Modal для подчинённой задачи;
- открывать Drawer для полноценного самостоятельного объекта;
- создавать новую модалку для каждого шага формы;
- позволять Body прокручивать Header и Footer;
- терять dirty data;
- добавлять Back без истории перехода;
- дублировать одно объектное действие в нескольких зонах;
- генерировать произвольные визуальные токены вне UI Kit.
