# Drawer — расширенные примеры содержимого и состояний

**Статус:** справочный слой, выделенный из ранней подробной дизайн-спецификации. **Не альтернативная норма**. Приоритет имеет [актуальный Drawer design contract](./drawer.md) и [runtime](../runtime/drawer.md), особенно темы NORM/ORM, внешний Close ORM, каскад без hard max=2, Escape off by default, неутверждённый Back и открытые вопросы. Указанные ниже композиции — примеры, не API существующего UI Kit.

# 11. Варианты Footer

```ts
type DrawerFooterVariant =
  | 'none'
  | 'single'
  | 'standard'
  | 'split'
  | 'stepper';
```

## 11.1. None

Использовать:

- для просмотра;
- для истории;
- для справочной информации;
- если все действия локальные;
- если закрытия достаточно.

## 11.2. Single

Одно основное действие.

```txt
[ Применить ]
```

Подходит:

- для простого фильтра;
- для подтверждения выбора;
- для завершения короткого шага.

В S и M кнопка может занимать всю доступную ширину.

## 11.3. Standard

Secondary + Primary.

```txt
[ Отменить ] [ Сохранить ]
```

Правила:

- действия равнозначно доступны;
- Primary справа;
- в узких Drawer кнопки могут занимать равные колонки;
- не дублировать Close действием «Закрыть», если это не отдельный пользовательский результат.

## 11.4. Split

Независимое или destructive действие слева, завершение справа.

```txt
[ Удалить ]                 [ Отменить ] [ Сохранить ]
```

Использовать, когда destructive action относится ко всему Drawer.

## 11.5. Stepper

Навигация по линейному сценарию.

```txt
[ Назад ]                   [ Продолжить ]
```

Не путать кнопку Footer «Назад» с Header Back:

- Footer «Назад» меняет шаг линейного процесса;
- Header Back возвращает предыдущий экран внутри Drawer;
- Close завершает работу с Drawer.

# 15. Паттерны содержимого

Drawer shell остаётся одинаковым. Содержимое формирует композиционные паттерны.

## 15.1. Filter Drawer

Назначение:

- полный набор фильтров;
- точная настройка выборки.

Рекомендуемый размер:

- S или M.

Footer:

- «Сбросить» + «Применить»;
- либо одно «Применить».

Правила:

- быстрые фильтры остаются на странице;
- Drawer содержит расширенный набор;
- активные фильтры после применения отражаются на странице;
- закрытие без применения не должно незаметно менять выдачу, если не используется live filtering.

## 15.2. History Drawer

Назначение:

- версии;
- изменения;
- авторы;
- даты;
- причины;
- источники.

Рекомендуемый размер:

- M;
- L для сложной истории.

Footer:

- обычно отсутствует.

Навигация:

- версия открывается через Replace content;
- самостоятельная сущность может открыться вторым Drawer.

## 15.3. Select entity Drawer

Назначение:

- поиск;
- фильтрация;
- выбор связанного объекта.

Рекомендуемый размер:

- M.

Footer:

- «Отменить» + «Выбрать»;
- «Привязать»;
- кнопка недоступна без выбора.

Правила:

- выбор не должен теряться при прокрутке;
- выбранное состояние явно видно;
- empty state объясняет, как найти объект;
- при одиночном выборе допустимо завершение по клику только для простого и безопасного сценария.

## 15.4. Create or Edit Drawer

Назначение:

- дополнительное создание;
- редактирование;
- настройка.

Рекомендуемый размер:

- S, M или L.

Footer:

- «Отменить» + «Сохранить»;
- «Назад» + «Продолжить» для шагов.

Правила:

- dirty guard обязателен;
- ошибки показываются рядом с полями и в summary при необходимости;
- Primary action не исчезает при прокрутке;
- длинные формы делятся на смысловые секции;
- ширина не увеличивается из-за формы.

## 15.5. Detail or Preview Drawer

Назначение:

- краткая связанная информация;
- доказательство;
- источник;
- объяснение;
- preview сущности.

Рекомендуемый размер:

- S или M;
- L при сложном составе.

Footer:

- обычно отсутствует;
- может содержать переход к полному объекту.

Не использовать как постоянную замену Object Modal.

## 15.6. Review and Approval Drawer

Назначение:

- предложение изменения;
- спор;
- комментарий;
- согласование локального шага.

Рекомендуемый размер:

- M или L.

Footer:

- действия решения должны быть фиксированы;
- destructive/reject и accept визуально различаются;
- причина и последствия решения должны быть понятны до действия.

## 15.7. AI Explanation Drawer

Назначение:

- объяснить вывод;
- показать источники;
- показать доказательства;
- раскрыть логику AI;
- дать связанный следующий шаг.

Рекомендуемый размер:

- M или L.

Правила:

- AI-блок привязан к текущему объекту;
- summary перед деталями;
- источники видимы;
- объяснение структурировано;
- Drawer не превращается в абстрактный чат;
- кнопка перехода к связанному объекту ведёт в правильный слой.

## 15.8. Workspace Drawer XL

Назначение:

- редкая широкая рабочая задача;
- сложная аналитика;
- большая композиция.

Рекомендуемый размер:

- XL.

Правила:

- использовать только системный XL;
- не создавать дополнительные ширины;
- проверить, не нужен ли Page или Modal;
- сохранить ту же анатомию и поведение;
- не использовать XL только потому, что текущая форма плохо скомпонована.

# 16. Состояния

Состояния находятся внутри Body и не создают отдельные варианты shell.

Поддерживаются:

- default;
- loading;
- empty;
- error;
- success;
- no access;
- dirty;
- submitting.

## Loading

- Header остаётся доступен;
- Close работает, если закрытие допустимо;
- Footer может быть disabled;
- skeleton повторяет структуру содержимого;
- не менять ширину и высоту Drawer.

## Empty

Empty state должен:

- объяснить, почему нет данных;
- дать следующий шаг;
- не выглядеть как ошибка;
- сохранять контекст задачи.

## Error

Error state должен:

- объяснить, что не удалось;
- содержать retry, если повтор возможен;
- не уничтожать введённые данные;
- не заменять Drawer неожиданным Dialog.

## Submitting

- Primary action показывает loading;
- повторное отправление блокируется;
- закрытие регулируется продуктовым риском;
- пользователь понимает, можно ли продолжать работу.

## Граница детализации

Точные размеры controls, цвета, токены, разрешённость закрытия по overlay, dirty-state UX, глубина stack, responsive и доступность требуют целевой проверки. Эта справка описывает **содержимое** и варианты Footer, а не утверждает реализацию JS/React-контрактов.
