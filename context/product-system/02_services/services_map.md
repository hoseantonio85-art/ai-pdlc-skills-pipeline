# NORM — единая карта сервисов

Актуализация по каноническим OpenSpec существующих сервисов, снимок `[редакция исходника удалена]` от 2026-10-14. Исходные технические спецификации в архив не включены; для повторной проверки используйте настроенные внешние источники.

## Принцип истины

- **Бизнес-факты и поведение существующих сервисов:** OpenSpec — первичный норматив; карта и карточки ниже — единое продуктово-ориентированное изложение, которое обновляется вслед за спецификациями.
- **UX/UI:** утверждённые task increment и UX/UI-паттерны могут задавать представление, но не заменяют доменную бизнес-логику.
- **Production:** наличие спецификации подтверждает наличие документированного сервиса/требования, не конкретный релиз или runtime-состояние.
- **Граница:** предметная область для пользователя ≠ технический микросервис.

**Исключение для текущей реализации «Мер»:** код проверенных снимков FE/BE 23.10.2026 имеет приоритет для AS IS (не подтверждает production); единственное развёрнутое описание — [`measures.md`](measures.md). Исторические OpenSpec по мерам остаются источником требований, а не автоматически подтверждённого поведения. Подробнее: [`source_authority.md`](../07_business_context/source_authority.md) и [`реестр открытых вопросов`](../07_business_context/measures_questions.md). Для всех остальных сервисов правило OpenSpec выше не меняется.

## Кто владеет какими объектами

- `risk-cloud`: риск, оценочный объект AI-агента / продукта, лимитная кампания и индивидуальные лимиты.
- `incident-cloud`: Событие и его последствия.
- `measure-cloud`: мера и её workflow.
- `contractors`: контрагент, договор, проверка.
- `company-cloud` / `employee-cloud`: компания/тариф/сотрудник и права.
- `dict-cloud`: справочник и его редакции.
- `attachment` / `library`: вложения / документы; база знаний — отдельная пользовательская задача.
- `link`: типизированные отношения объектов; `semantic-search`: сервис поиска; `gateway` и shell — контуры платформы.

## Сквозные сценарии

1. Событие → последствия / расследование → связь с риском → пересмотр риска и/или мера; ссылки не переносят владельца данных.
2. Риск → финансовые показатели / лимитная кампания → индивидуальный лимит → согласование и использование.
3. Агент/продукт → документы → оценочная задача → результаты риска → меры/рекомендации. **У разных объектов собственный workflow.**
4. Контрагент → договор → проверка → решение / связанные документы.
5. Компания/сотрудник/тариф → разрешённые сервисные действия; реальные права определяются конкретным разрешением, ролью и профилем tenant.

## Правила для AI PDLC

- По задаче найдите область в `07_business_context/service_registry.yaml`, откройте релевантное полное описание из `02_services/`; для `measures` сопоставляйте AS IS с проверенным кодом из описания, для остальных сервисов — с внешним OpenSpec, доступность которого подтверждена через YAML.
- Не домысливайте права, статусы, формулы, обязательность полей и UI-availability, если есть точный источник.
- Не запрещайте проектировать лимитную кампанию: домен подтверждён актуальными спецификациями. «Объект оценки» является понятием в модели рисков и не обязательно самостоятельным пунктом меню.
- При обновлении OpenSpec синхронно обновляйте эту карту, карточки, компактные реестры, ссылки на источники и валидатор; никаких overlay или конкурирующих бизнес-контекстов.
- Для UI используйте действующие UX/UI-паттерны и выбранный режим Product Fidelity / Concept Exploration, а не переносите в прототип техническую схему backend.
