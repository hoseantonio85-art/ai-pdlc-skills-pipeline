# UX patterns NORM

Используй паттерны как систему выбора, а не как обязательный шаблон каждого экрана. Сначала определи намерение, данные и решение пользователя; затем выбери surface.

Паттерн — сильная отправная точка, а не клетка. Сохраняй product invariants и проверенную interaction semantics, но адаптируй композицию, если данные или пользовательская задача этого требуют. Если существующие patterns не подходят достаточно хорошо, допустимо предложить новую композицию: объясни, что сохраняется из системы, почему нужен deviation и пометь решение как `composition-adaptation` / `new-pattern-candidate`. Не создавай новую визуальную систему ради новизны.

## 1. Collection presentation

Перед выбором визуального списка определи решение пользователя:

- decision-oriented entities → Card registry / row-cards;
- выбор категории/области → Navigation collection / card grid;
- документы и контент → Compact content/file list.

Не заставляй любую коллекцию выглядеть как карточка сущности. Классическая таблица не используется как основной decision registry, но локально допустима для истории и прямого сравнения однородных данных.

### Card registry

Основной способ показать множество рисков, мер, инцидентов и других объектов.

Строка-карточка должна помогать решить, какой объект открыть или обработать первым. Покажи название, статус/сигнал, причину внимания, 1–3 ключевых признака и доступное действие. Допускай колонкообразное выравнивание между карточками.

Не используй классическую таблицу как основной реестр. Локальная табличная сетка допустима для истории изменений и прямого сравнения однородных значений.

## 2. Page header

Покажи название рабочей области и осмысленный счётчик. Размещай справа только контекстные действия, которые относятся ко всей странице. Не перегружай header действиями над отдельными объектами.

## 3. Filter toolbar, quick filters and attention zones

Для desktop используй единый filter toolbar по умолчанию:

`[ segmented scope ] [ chip ] [ chip ] …     [ search ] [ filtering utilities ] [ advanced filter ]`

- `segmented scope` — optional: 2–несколько взаимоисключающих устойчивых вариантов, например «Все / Мои». Это segmented control, а не binary Switch.
- Quick filter chips идут непосредственно после segmented control и отражают частые понятные способы фокусировки.
- Search, secondary filtering utilities и advanced-filter trigger группируются справа в той же строке.
- Если search вторичен, его можно раскрывать по запросу; раскрытое поле может занять отдельный нижний ряд как состояние паттерна.
- Перенос toolbar на несколько строк допустим из-за ширины/responsive или task-specific причины, а не как default desktop composition.
- Полный набор фильтров открывай в drawer. Показывай компактный индикатор активного расширенного фильтра.
- Quick filter должен запускать понятный сценарий, а не повторять случайное поле модели данных.

## 4. Dashboard / situational overview

Используй для обзора ситуации, мониторинга, сравнения и поиска зон внимания. Каждый агрегат или график должен вести к фильтрации, исследованию или действию. Dashboard или compact situational overview может сочетаться с card registry.

Для registry/monitoring page явно проверь, есть ли агрегированный вопрос, который пользователь поймёт быстрее через распределение, динамику, концентрацию, coverage или визуальную зону внимания, чем через последовательное чтение карточек. Если такой сигнал есть — покажи ситуацию до detailed list или между controls и list, в зависимости от того, на что действуют фильтры. Если полезного aggregate story нет — не выдумывай аналитику.

Если chart/segment естественно связан с detailed list, его выбор должен фильтровать, подсвечивать или открывать соответствующие объекты, а active analytical state должен быть видим.

Не создавай декоративную стену KPI и не применяй dashboard только потому, что данных много.

## 5. Summary-first

Используй, когда пользователю иначе пришлось бы самостоятельно собирать вывод из нескольких сигналов. Summary отвечает: что происходит, почему важно и что делать дальше.

`Attention summary` может показывать зоны внимания карточками/сегментами с count или semantic state и вести к фильтрации / drill-down. Это не обязано быть dashboard.

Summary разрешён как характерный слой NORM, но не добавляй его автоматически: он должен давать новую смысловую или навигационную ценность и не дублировать quick filters без причины.

## 6. Object Modal

Открывай самостоятельный объект из множества в большой modal, если важно сохранить список и его фильтры. Для последовательного разбора допускай previous/next.

Внутри Object View сначала покажи смысл и состояние объекта, затем содержание, связи и meta. Разделяй основную область и правый rail, когда это помогает сканированию.

Target read-only Object View использует единую правую action/meta zone без общего Footer. Current/legacy product views с Footer остаются evidence текущего состояния, но не должны автоматически переноситься в новую target-композицию. Create/edit использует стабильный footer для commit-действий.

## 7. Drawer

Используй для подчинённой задачи: фильтра, выбора, настройки, пояснения, поиска связи или дополнительной работы внутри modal. Drawer должен сохранять состояние родительской поверхности.

Не открывай полноценный самостоятельный объект в drawer. Не делай drawer промежуточным шагом перед Object Modal без пользовательской необходимости.

## 8. Floating action dock

Используй нижнюю плавающую панель, когда основное действие или AI/chat должно оставаться доступным при исследовании длинной поверхности. Сочетай одно primary action с ограниченным числом вспомогательных действий. Резервируй место под панель и упрощай её на mobile.

Это узнаваемый паттерн NORM, но он не нужен на экране без постоянного следующего действия.

## 9. AI blocks

Привязывай AI к конкретному объекту, ситуации или действию. Показывай полезный результат: summary, объяснение, гипотезу, рекомендацию или подготовленное действие. Обозначай неопределённость и оставляй решение человеку.

Не используй абстрактный чат без контекста как замену UX-решению.

## 10. States

- Empty объясняет, почему данных нет и какой следующий шаг доступен.
- Loading сохраняет структуру ожидаемого экрана, если это помогает ориентации.
- Error объясняет последствия и предлагает восстановление.
- Partial показывает доступные данные и явно обозначает пробел.
- Action progress предотвращает повторный запуск и сообщает результат.

## 11. Surface decision

Перед проектированием ответь:

1. Пользователь обозревает множество, исследует объект или выполняет подчинённую задачу?
2. Нужно ли сохранять исходный контекст?
3. Какой сигнал влияет на решение?
4. Какое действие завершает сценарий?

Выбери:

- page — самостоятельная рабочая область;
- card registry — принятие решений по множеству;
- dashboard — обзор и зоны внимания;
- Object Modal — самостоятельный объект поверх множества;
- drawer — подчинённая задача;
- regular modal — короткое решение или компактная форма;
- inline — локальная деталь или действие.

Page, Object Modal и long-lived workspace могут переиспользовать близкую композиционную модель (например, main content + contextual rail), если меняется только роль surface, а interaction/navigation contract остаётся корректным. Surface type не требует искусственно новой сетки.

## Anti-patterns

- равнозначный набор блоков без информационного приоритета;
- классическая таблица как основной список объектов;
- карточки, показывающие все поля без отбора;
- summary, не уменьшающая работу интерпретации;
- dashboard без drill-down или действия;
- самостоятельный объект в drawer;
- read-only Object View с дублирующим footer;
- смешивание content и технической meta;
- цвет как единственный носитель статуса;
- дублирование одного действия в нескольких местах без причины;
- AI без контекста и понятной ценности.
