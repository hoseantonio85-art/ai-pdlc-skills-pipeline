# AI PDLC Skills Pipeline — публичный установочный комплект

**Назначение:** обезличенный стартовый AI PDLC pipeline для GigaCode. **Не содержит** внутренних данных реального продукта, исходного кода, внутренних OpenSpec, UI Kit, логотипов и фирменных HTML-референсов. Реальное продуктово-специфическое качество достигается после подключения **разрешённого** локального контекста и источников. Версия — **public review 2026-10-28**. Это функциональный универсальный pipeline с **демонстрационным продуктовым контекстом**, не эквивалент внутренней product-specific сборки.

> **Важно:** автоматическая очистка и поиск строк не заменяют юридическую проверку и согласование с ИБ. До публикации, особенно в публичном репозитории, передайте файл ответственному специалисту ИБ. Не загружайте рабочие закрытые версии на общедоступные ресурсы.

## Структура

```text
skills-pipeline/
├── agent/
│   └── .gigacode/
│       ├── skills/                      # 00, 01, 02, 03, 03-5, 04, 05-07
│       ├── agents/                      # frontend-planner / implementer / reviewer
│       ├── product-contexts.yaml.example
│       ├── product-context.yaml.example
│       └── product-evidence.yaml.example
├── context/
│   ├── product-system/
│   │   ├── 01_foundation/                # базовая модель продукта — demo
│   │   ├── 02_domain/                   # условные объекты, сервисы и реестры — demo
│   │   ├── 03_ux/                       # общие UX-принципы
│   │   ├── 04_ui/                       # общие UI-паттерны и нейтральный HTML-starter
│   │   ├── 05_external/                 # политика источников
│   │   └── context-manifest.yaml
│   └── tools/validate_context.py
└── README.md
```

Внутри архива **нет** ни ZIP/TGZ, ни внутренних спецификаций, ни имен и адресов внутренних репозиториев, ни конкретных данных настоящего продукта. Нейтральный product context нужен только для проверки работы конвейера.

## Установка GigaCode

1. Скопируйте папки из `agent/.gigacode/skills/` в `~/.gigacode/skills/`; три файла из `agent/.gigacode/agents/` — в `~/.gigacode/agents/`. **Старые одноимённые скиллы без номеров предварительно архивируйте локально и отключите**, чтобы не выбирать устаревший вариант.
2. Папку `context/` храните там, где удобно. Она не должна находиться внутри каждого frontend-проекта.
3. Из `agent/.gigacode/product-contexts.yaml.example` создайте `~/.gigacode/product-contexts.yaml` и установите абсолютный путь **до корня** `context/` в `contexts.sample_product.provider.root`. Имя `sample_product` — демонстрационное.
4. Из `agent/.gigacode/product-context.yaml.example` создайте `<рабочий-проект>/.gigacode/product-context.yaml`, где `context_id: sample_product`. Этот selector относится к рабочему проекту, а не ко всем проектам.
5. Из `agent/.gigacode/product-evidence.yaml.example` при необходимости создайте `~/.gigacode/product-evidence.yaml`, заполняя локальные пути или согласованные ссылки на спецификации и UI Kit. Этот файл **не коммитить**. Можно оставить все поля пустыми, если источники ещё не подключены.
6. Выполните `python -X utf8 context/tools/validate_context.py` (PyYAML: `python -m pip install pyyaml`). В GigaCode откройте новую сессию или выполните `/clear`.

## Три YAML и внешний evidence YAML

| Файл | Расположение | Назначение |
|---|---|---|
| `product-contexts.yaml` | `~/.gigacode/` | Где находится контекст (provider root, manifest) |
| `product-context.yaml` | `<project>/.gigacode/` | Какой `context_id` используется в этом проекте |
| `context-manifest.yaml` | `context/product-system/` | Какие файлы читать на каждом этапе |
| `product-evidence.yaml` | `~/.gigacode/` | **Откуда читать внешние** спецификации, документацию UI Kit и target repos — локальные пути и/или разрешённые URL |

**Путь или URL сам по себе не даёт агенту доступ.** Он должен проверить доступность через свои инструменты, требуемые права и фактическую версию; при недоступности сообщить `NEEDS_SOURCE` или `BLOCKED_BY_SOURCE`. Секреты, cookies, токены и внутренние URL не включать в публичные файлы. Реальные источники подключайте только в разрешённой рабочей среде.

## Начало работы

Этапы: **01 Intent + Brief → 02 UX Solution → 03 HTML prototype → 03.5 UX Sync → 04 Product SDD → 05 frontend-plan → 06 implementation → 07 review**. На 05–07 применяются `05-07-frontend-standards` и соответствующие субагенты. Произнесите в GigaCode: «Проверь context preflight, назови `context_id`, manifest и локальные источники, которые действительно доступны». Для реальной задачи передайте её исходные материалы и разрешённый продуктовый контекст; **не используйте демонстрационный контекст как бизнес-истину**.

## Изменения и безопасность

В публичном шаблоне сознательно **нет** внутренних бизнес-правил, согласовательных процессов, деталей реальных сервисов, исходных снимков, фирменных компонентов, проектных идентификаторов, настоящих репозиториев и примеров с реальными пользователями. Это снижает риск раскрытия, но **не гарантирует одобрение ИБ**. Проверку необходимости публикации самого процесса/скиллов проводит владелец информации.

## Skill 00 — описание продукта/сервиса

`00-capture-product-service-context` помогает системно создавать бизнес-описания сервисов, интервьюировать владельцев, фиксировать решения и неизвестные факты. Входит в public kit с полностью демонстрационными примерами; не требует публикации какого-либо реального продуктового контекста.

## Что не публикуем

Подробные сервисы и бизнес-реестры настоящего продукта, OpenSpec/БТ, UI Kit package, частные HTML-референсы и исходники **не входят** в этот репозиторий. Их подключают **отдельно в разрешённой среде** через `~/.gigacode/product-contexts.yaml`, `<project>/.gigacode/product-context.yaml`, `~/.gigacode/product-evidence.yaml`.

Автоматическая проверка контента не даёт разрешения на публикацию по правилам конкретной организации. Код и материалы проходят независимое согласование владельца/ИБ.
